# Roadmap Format Standard

**Purpose**: Define `specs/ROADMAP.md` as a generation contract: the whole file is rendered from
`specs/state.json`, in a fixed three-part order, and nothing in it is hand-authored. This file
states which state field each rendered line comes from, which content is deliberately not
rendered, and the patterns a reader matches against.

---

## Placement

`specs/ROADMAP.md` is a single generated file at the repository's `specs/` root (or at
`roadmap_context.output_path` when the store names another repository-relative path). It is a
review surface: a collaborator reads the status of the next milestones from its first screen.
Per-task detail lives in `specs/TODO.md`; reasoning that does not fit a bounded field lives in a
decision record, with a one-line pointer here.

The file's first line is the generated sentinel, byte-exact:

```
<!-- generated by roadmap-integration.sh from specs/state.json; do not edit -->
```

A file carrying that line is owned by the generator. A file without it is hand-authored content
the generator cannot reproduce and refuses to overwrite (see "Destructive-Overwrite Refusal").

## Section Order

Exactly three parts, in this order:

| # | Part | Source |
|---|------|--------|
| 1 | Intro: `# Roadmap`, the primary goals, a milestone status table, a link to the last part | `primary_goals` (else `active_goal`), `roadmap_milestones[]` |
| 2 | One section per milestone, in array order | `roadmap_milestones[]`, its nested `batches[]`, `active_projects[]`, the archive |
| 3 | `## Rules, conventions and repo context` | `roadmap_context`, `active_projects[]` |

Array position is order, for milestones and for the batches inside one. No priority field
exists at either level.

### Part 1: Intro

```
<!-- generated by roadmap-integration.sh from specs/state.json; do not edit -->
# Roadmap

- {primary_goals[0]}
- {primary_goals[1]}

| Milestone | Status | Tasks done | Review |
|---|---|---|---|
| [{id}: {title}](#milestone-{id lowercased}) | {status} | {done}/{total} | {review state} |

See also: [Rules, conventions and repo context](#roadmap-context)
```

- One bullet per `primary_goals` entry. A store with no `primary_goals` renders a single bullet
  from `active_goal`.
- One table row per milestone; a closed milestone's status cell reads `closed {date}`. The link
  target derives from the stored `id` (lowercased, every character outside `[a-z0-9_-]` replaced
  by `-`), never from the title, so a retitle does not break a link. A store holding no milestone renders
  `_No milestones recorded._` in place of the table.
- The table is the dashboard: status, progress and review state for every milestone are visible
  without scrolling past the intro.

### Part 2: Milestone sections

An open milestone (`progress.status` of `planned` or `active`):

```
<a id="milestone-{id lowercased}"></a>
## {id}: {title}

{aim}

- **Progress**: {status} -- {batches done}/{batches} batches, {tasks done}/{tasks} tasks done[ -- {progress.note}]
- **Review**: {review.state}[ on `{review.ref}`][, {review.request}][ (updated {review.updated})]
- **Gate**: {gate}

**Batch 1** -- {description}[ ({done}/{total} done)]
```
/orchestrate {open member ids, comma-separated}[ {flags}]
{id} {token}  {title}[   <- {roadmap_annotation}]
```
```

- The `Progress` counts are derived at render time from member status; only `status`, `closed`
  and `note` are stored. A milestone with no batch renders `{status} -- no batches yet`.
- The `Review` line renders the stored `review` object. It is never fetched from a forge at
  render time, so rendering stays offline and deterministic; `updated` is shown so a stale value
  is visible. An absent `review` object renders state `none`.
- The `Gate` line is present only when `gate` is stored. It carries the closing criterion, never
  a dated measurement against it.
- A batch's fenced block opens with the `/orchestrate` line naming only its open members, then
  one line per member: number and status token padded to a 20-column description start, the
  task's `title` cut with a trailing `...` so the line stays at or under 100 characters, and an
  optional `   <- {roadmap_annotation}` suffix. Lines sort by token rank, then by number.
- A batch with no open member is the single line `**Batch N** (done) -- {description}`, with no
  fenced block.
- A closed milestone is its anchor, its heading and one line:
  `Closed {progress.closed}[ -- {done}/{total} tasks done] -- review: {review line}[ -- {note}]`.
  Its batches are not listed.

### Part 3: Rules, conventions and repo context

```
<a id="roadmap-context"></a>
## Rules, conventions and repo context

### Repository
- {roadmap_context.overview[]}

### Rules
- {roadmap_context.rules[]}

### Conventions
- {roadmap_context.conventions[]}

### Open tasks in no batch
```
{id} {token}  {title}
```
```

An empty subsection is omitted. `### Open tasks in no batch` lists every open task that no batch
of a non-closed milestone names, in the same line shape as a batch member, so a task that was
never scheduled stays visible. This part is last so reader context never sits between a reviewer
and the milestones.

## State Fields and Bounds

| Field | Bound | Rendered as |
|---|---|---|
| `primary_goals[]` | 500 characters per entry | intro bullets |
| `roadmap_milestones[].id` | `^[A-Za-z0-9][A-Za-z0-9._-]{0,15}$`, unique | heading, anchor, table link |
| `roadmap_milestones[].title` | 80 | heading, table link |
| `roadmap_milestones[].aim` | 300 | paragraph under the heading |
| `roadmap_milestones[].gate` | 400, optional | `Gate` line |
| `roadmap_milestones[].progress` | `status` in `planned`/`active`/`closed`; `closed` date iff closed; `note` 140 | `Progress` line, table |
| `roadmap_milestones[].review` | `state` in `none`/`prepared`/`in_review`/`changes_requested`/`approved`/`merged`; `ref`, `request`, `updated` optional | `Review` line, table |
| `roadmap_milestones[].batches[]` | `task_ids` non-empty; `description` 100; `flags` optional | batch line and block |
| `roadmap_milestones[].batches[].rationale` | unbounded | **not rendered** (kept for the next judgment pass) |
| `roadmap_context.overview[]`, `.rules[]`, `.conventions[]` | 300 per entry | last part |
| `roadmap_context.output_path` | repository-relative; absolute and `..` refused | where the file is written |
| `active_projects[].roadmap_annotation`, `.roadmap_ext_blocked` | per the schema | member-line suffix, `EXT-BLOCKED` token |

`context/formats/roadmap-entry-template.md` holds the entry templates and the worked examples for
the bounded prose fields. Every bound is enforced by `scripts/validate-state.sh` and declared in
`context/schemas/state-schema.json`; the two move together.

## Status Tokens

A closed vocabulary with a precedence rule for an open member. The first matching row wins:

| Precedence | Token | Source |
|---|-------|--------|
| 1 | `HOLD` | `state.json` `status == "hold"` |
| 2 | `IN FLIGHT` | `status == "implementing"` |
| 3 | `BLOCKED` | `status == "blocked"` |
| 4 | `PARTIAL` | `status == "partial"` |
| 5 | `EXT-BLOCKED` | the task entry's `roadmap_ext_blocked` field (boolean, schema-backed) |
| 6 | `blocked:N[,M...]` | `dependencies[]` intersected with the non-terminal task set is non-empty; sorted ascending comma list |
| 7 | `ready` | `dependencies[]` intersected with the non-terminal task set is empty |

Rows 1-4 derive from the task's own `status`; rows 6-7 derive from `dependencies[]` and apply only
when none of rows 1-5 match. Row 5 is checked before the dependency filter because an
externally-blocked task may otherwise read `ready` or `blocked:N` against in-repo data alone.

Two further tokens mark a member that is not open:

| Token | Meaning |
|---|---|
| `done` | terminal in `active_projects`, or absent from it and present in any list of the sibling `archive/state.json` |
| `missing` | found in neither place; `validate-state.sh` Check 13 owns reporting it |

A batch's `task_ids` MAY name tasks carrying `dependencies[]` edges among themselves:
`/orchestrate` dispatches dependency-aware waves, so an intra-batch edge sequences the two tasks
into successive waves rather than disqualifying either one. See
`context/patterns/batch-orchestration-guardrails.md`'s Gate Catalogue.

## Judgment and Rendering

`roadmap-agent` (dispatched by `skill-roadmap` for `/roadmap`) decides which milestones exist,
their aims and gates, batch membership, batch order, descriptions and missing dependency edges,
and writes those decisions to state through `state-write.sh`. `scripts/roadmap-integration.sh`
renders what state holds and exercises no judgment; it reads nothing back out of the file it
writes. A second consecutive `--regenerate` with no intervening state change is byte-identical.

## Pruning Ledger

Each section a hand-authored roadmap of the eight-section layout (`## Goal`, `## Gate state`,
`## Next`, `## Open work`, `## Checks before and after every call`, `## Settled decisions`,
`## Standing rules`, `## Unfiled observations`) carries, the reader found for it, and its
disposition in the generated file:

| Content | Reader found | Disposition |
|---|---|---|
| Italic preamble (forward-only policy, a last-measured date) | none; a hand-kept date goes stale | Not rendered. The sentinel line states the file's provenance. |
| `## Goal` | people | Kept, as the intro's `primary_goals` bullets. |
| `## Gate state` | none mechanical; dated measurements | Not rendered. A measurement belongs to the run that produced it; the milestone `gate` field carries the criterion, which is what a reviewer needs. |
| `## Next` lead-in and closing paragraphs | none | Not rendered; no state field. |
| `## Next` fence of `/orchestrate` lines | people; the next-batch suggester reads the state entries | Kept, regrouped under milestones, one block per batch. |
| `## Next` "Why this order" prose per batch | `roadmap-agent`'s next pass, from state | Not rendered. The `rationale` state field keeps it. |
| Coverage appendix of uncovered tasks | none | Not rendered. `### Open tasks in no batch` answers the same question without chunking tasks into proposed runs, which would be judgment. |
| `## Open work` topic blocks | people; duplicates `specs/TODO.md` | Not rendered as a section. Each batch lists its members with the same status tokens; only tasks in no batch keep a list. |
| `## Open work` trailing prose | none | Not rendered; no state field. |
| `## Checks before and after every call` | people, occasionally | Kept, as bounded `roadmap_context.conventions` items. |
| `## Settled decisions` | people | Kept, as bounded `roadmap_context.conventions` items, each ideally one line pointing at a decision record. |
| `## Standing rules` | people | Kept, as bounded `roadmap_context.rules` items. |
| `## Unfiled observations` | none; by its own title nothing in it is worth a task | Not rendered. |

Nothing a migration finds is discarded: content with the disposition "not rendered", and any
item over its field bound, is moved verbatim to a retained-prose file by
`scripts/migrate-roadmap-to-milestones.sh` (see "Migration").

### Rejected alternatives

- **Keep some sections hand-authored and regenerate the rest.** A file with both kinds of text
  needs a parser that reads authored content back out of the file about to be overwritten, and
  the authored remainder is exactly the part that grows unread. A single owner per file removes
  both problems.
- **Render `rationale` under each batch.** Multi-paragraph ordering prose per batch runs to
  several screens and pushes the milestone status a reviewer came for out of view. The field
  stays in state for the agent that revises the order.
- **Fetch review state from the forge at render time.** Rendering would need network access and
  credentials, would differ between two runs on the same state, and would fail inside an
  unattended conclusion step. A stored `review` object with its `updated` date is deterministic
  and makes staleness visible.
- **Store progress counts.** A stored count drifts from the member statuses it summarizes. The
  counts are derived at render time; only the status decision, the closure date and a one-line
  note are stored.
- **Classify a file by its section headers.** Header text cannot distinguish generated text from
  authored text and drifts by rename. One fixed sentinel line is unambiguous.

## Generation

Generated by `scripts/roadmap-integration.sh`:

- `--print` (default): emits the whole rendered file to stdout; reads no existing roadmap and
  mutates nothing.
- `--regenerate`: writes the rendered file in place, subject to the refusal below.
- `--prune`: a deprecated alias for `--regenerate`. A file rendered from live state accumulates
  no terminal entries, so a separate prune pass has nothing to remove. Prints one stderr
  deprecation note, then performs `--regenerate`.
- `--dry-run` (with either write mode): prints a diff, writes nothing.
- `--state PATH`, `--roadmap PATH`: override the store and the output path. Without `--roadmap`
  the output path is `roadmap_context.output_path`, else `specs/ROADMAP.md`.

Batches and the output path are read through `scripts/lib/roadmap-entries-lib.sh`;
`scripts/lib/status-vocabulary.sh` anchors the terminal status set. No wave or DAG algorithm is
involved: the per-member `blocked:`/`ready` derivation is a one-pass filter over `dependencies[]`.

### Destructive-Overwrite Refusal (permanent property)

Before a write mode touches the output path, `scripts/lib/roadmap-preflight-lib.sh` classifies
it. The sentinel is tested first:

| Verdict | Meaning | Write mode |
|---|---|---|
| `generated` | first line is the sentinel | overwrite |
| `absent` | no file | write only when `roadmap_milestones` is non-empty; otherwise a no-op `NOTE:` |
| `classic` | hand-authored, eight-section layout | refuse |
| `stage` | hand-authored, `## Stage N` layout with a fenced `/orchestrate` block | refuse |
| `unknown` | hand-authored, any other shape | refuse |

A refusal is a named reason on stderr carrying `(verdict: X)`, the expected sentinel, the file's
own `## ` headers and the name of `migrate-roadmap-to-milestones.sh`; exit status 1; and no
write, with or without `--dry-run`. No flag overrides it. With no authored content in the render
path, a wrong overwrite would cost the whole document, so the generator never guesses.

The library's `scaffold` action writes the sentinel line alone onto an absent path and refuses
every other path; a hand-authored file is routed to the migration.

### Migration

`scripts/migrate-roadmap-to-milestones.sh` moves a store holding flat `roadmap_batches` /
`roadmap_notes` and a hand-authored roadmap to the milestone shape, once:

- It is mechanical. Every flat batch goes unchanged, in order, under one milestone `M1`
  ("Current work", `active`, review `none`). Dividing the work into real milestones is
  `roadmap-agent`'s judgment, made afterwards through `/roadmap`.
- `## Goal` paragraphs become `primary_goals`; `## Standing rules` items become
  `roadmap_context.rules`; `## Checks` and `## Settled decisions` items become
  `roadmap_context.conventions`.
- An item over its field bound is never truncated: it is retained whole. Every other section,
  non-item prose, the preamble and every `roadmap_notes` string go verbatim to the retained-prose
  file (default `archive/roadmap-retained-prose-YYYYMMDD.md` beside the state file, or the
  `--retained` path). An existing retained-prose file is never overwritten.
- **Losslessness gate**, run before any write: the multiset of source lines must equal the
  retained file's lines plus the recorded source lines of every item placed in state; each state
  item must equal its recorded lines joined; and the batches must be equal under `jq -S`. A
  failure writes nothing and names the unaccounted lines.
- Write order: the retained file, then state (through `state-write.sh`, deleting the flat keys),
  then the generated roadmap.
- Exit status: 0 success; 1 usage error or gate failure; 2 refused (the store already holds
  milestones and `--force` was not given, or the retained target exists); 3 a prerequisite
  migration (`migrate-roadmap-next-to-state.sh`) has not run.

### Stderr Marker and Failure Diagnostics

Every invocation that reaches mode dispatch -- i.e. passes argument validation -- prints one
always-present machine-readable stderr marker, on success AND on failure:
```
<!-- roadmap-generation mode=M tasks=N topics=T runs=R pruned=P retained=A -->
```
`runs=` is the number of batches under milestones that are not closed; `pruned=` and `retained=`
are always `0`. The marker never affects the exit code. `--help` and a usage error (an unknown
flag, a missing `--state` file) happen before mode dispatch and print only their own message. A
failure after that point additionally emits one named stderr line first:
```
ERROR: roadmap-integration.sh failed (mode=M) at line L: exit status N
```
The marker's six-field shape is frozen; a refusal or a crash is diagnosed through the separate
`ERROR:` line, never by adding a field to the marker.

**`OUTCOME:` line**: the marker's count fields are identical between a write that changed the
file and one that left it unchanged. Both write modes additionally emit one `OUTCOME:` line to
stderr, immediately before the marker, in one of four shapes:
```
OUTCOME: --regenerate rewrote {path} (layout=generated, content changed)
OUTCOME: --regenerate left {path} unchanged (layout=generated, no content change)
OUTCOME: --regenerate --dry-run diffed {path}; wrote nothing (layout=generated, content would change)
OUTCOME: --regenerate --dry-run diffed {path}; wrote nothing (layout=generated, no content change)
```
`--prune` emits the same shapes with `--prune` substituted. `--print`, the absent-path no-op and
a refusal emit no `OUTCOME:` line: none of them reaches a write.

## Parsing Patterns Summary

| Element | Pattern |
|---------|---------|
| Sentinel (line 1) | `^<!-- generated by roadmap-integration\.sh from specs/state\.json; do not edit -->$` |
| Milestone anchor | `^<a id="milestone-([a-z0-9_-]+)"></a>$` |
| Milestone heading | `^## ([A-Za-z0-9][A-Za-z0-9._-]{0,15}): (.+)$` |
| Batch line | `^\*\*Batch (\d+)\*\*( \(done\))? -- (.+)$` |
| Run line | `^/orchestrate ([\d, ]+)(\s+(-\S.*))?$` |
| Member line | `^(\d+) (\S+( \S+)?)\s{2,}(.+?)(\s{3}<- (.+))?$` |
| Status token | `HOLD\|IN FLIGHT\|BLOCKED\|PARTIAL\|EXT-BLOCKED\|blocked:[\d,]+\|ready\|done\|missing` |
| Stderr marker | `^<!-- roadmap-generation mode=(\S+) tasks=(\d+) topics=(\d+) runs=(\d+) pruned=(\d+) retained=(\d+) -->$` |
| `OUTCOME:` line | `^OUTCOME: --(regenerate\|prune)( --dry-run diffed \| rewrote \| left )(.+?)(; wrote nothing\| unchanged)? \(layout=generated, (content changed\|no content change\|content would change)\)$` |

No tool parses the rendered file for batches: every reader (`orchestrate-suggest-next-batch.sh`,
`lint/lint-roadmap-batch-proposals.sh`) reads state through `roadmap-entries-lib.sh`.

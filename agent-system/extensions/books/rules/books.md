# Books Development Rules

Non-negotiables for authoring, certifying and documenting a **lean book**: a certified unit
inside a Lake package, named by a `book <Name>` command in its own book module. Each item below
states its measured failure mode, not just the rule.

## 1. Facts in Lean, judgments in TOML, everything else computed

A code module carries exactly two things: `@[book_export]` on a declaration (no kind argument —
the kind is derived from `getOriginalConstKind?`) and one `book_layer <layer>` line. The six
book-module fact commands — `book`, `book_assume`, `book_not_claimed`, `book_axioms`,
`book_policy`, `book_requires` — and `#book_ledger` belong to the **book module**, never to a
code module. The certifier warns on a fact command found in a code module; do not author one
there to "save a hop."

## 2. `book.cert.json` sits directly in the book directory and is the only non-Lean input

Every non-Lean tool (`books-tool`, the certify driver, any future reconciliation or book-health
tooling) reads `book.cert.json` and nothing else as its record of truth. Never a
`certificate/` subdirectory — the framed_channel export tooling treats every `certificate`
directory as a discovery root, so nesting the certificate there corrupts that discovery.

## 3. The flattened book-directory layout

A book directory is `<package-dir>/books/<name>/`, and `book.toml`, `book.cert.json` and
`book.typ` sit **side by side** in it — never `docs/book.typ` under a `docs/` subdirectory. This
is the current and future convention (the design record's Decision 1, as amended); an older
book still carrying `docs/book.md` under a `docs/` segment is legacy-and-held, not a model to
copy. A multi-file `docs/` entry remains legal in the schema but is not the modelled case here.

## 4. Explicit per-module lakefile `globs`, never a wildcard

Declare each module's lakefile `globs` entry explicitly. Never author a wildcard like `Books.+`:
when two packages each claim the shared `Books` root (as `books/lean`'s library root `Books` and
`books/tool`'s package both do), a wildcard glob makes each package claim the other's modules,
and the build fails with `bad import 'Books.Meta'`. This is a measured failure, not a
theoretical one — it is the exact error produced by a `Books.+` glob in a tree with two
`Books`-rooted packages.

## 5. Licence-header-then-`module` line order

The licence header comment must sit within the first three lines of every `.lean`/`.sh` file,
and in a file carrying Lean's `module` keyword, the header comment is line 1 and `module` is
line 2 — because a comment parses ahead of the `module` keyword, so the header must come first
for the file to remain a valid `module` file. This is a **structural** invariant, not a style
preference. The consuming repository's own SPDX header check (its
`components/framed_channel/scripts/check-spdx.sh`) enforces the exact header text; this rule
states the line-order invariant, not the header's literal wording.

## 6. Never hand-edit a generated artifact; never author a computed field

`book.cert.json` is generated by the certifier. A generated Typst fragment (e.g. a rendered
`book.typ` section produced by a documentation stage) is generated the same way. Hand-editing
either corrupts the record of truth the next certification run depends on. Likewise, never
author a field in `book.toml` that the certifier computes from the module graph (layers,
exports, dependencies, the permitted axiom set, assumptions) — `book.toml` holds judgments only;
everything derivable belongs to the book module and is computed by the certifier, never
duplicated by hand.

## Scope Boundary

This rule governs book-directory layout, book-module/code-module content, and the
facts/judgments/computed split. It does not cover originating or mathematically verifying the
underlying Lean content — that is `lean4`/`cslib`/`formal` territory. See
`context/project/books/README.md` for the navigation stub into the fuller domain corpus.

**`sapience_handoff` has no explicit ruling.** It is named only in enumerations (the four-tool grant list, the vault-model.md inventory). No file states "we considered re-expressing session-closing handoff notes as `sapience-remember.sh` calls and rejected it because X" or "handoff notes are out of scope because Y." Acceptance criterion 1 ("every prescribed write routes through `sapience-remember.sh`") is satisfied only in the narrow sense that nothing currently *prescribes* calling `sapience_handoff` — but deliverable (a)'s own text asks for an affirmative ruling to be *recorded*, which is currently absent.

**The test-file naming mismatch.** `scripts/tests/test-sapience-capture.sh`'s own header comment describes it exclusively as covering `sapience-retrieve.sh`'s exit-code split and cold-start retry (9 cases, all against `sapience-retrieve.sh`). Despite the generic name ("capture"), there is no case anywhere in the file that invokes `sapience-remember.sh`. The dispatch's deliverable (d) explicitly names this file as "the precedent for test siting and style" — the natural reading is to extend this same file with new cases for `sapience-remember.sh --dry-run`, following its existing `build_scratch`/stub-PATH-shadowing conventions (it would need its own `build_scratch` copying `sapience-remember.sh` instead of/alongside `sapience-retrieve.sh`, and since `--dry-run` makes no network call, no curl stub is even required for the core assertions — only `jq` on stdout, checking for `[repo:<slug>]` in `.provenance` and `"***REDACTED***"` for `.token`).

**`sapience-remember.sh --dry-run` already does exactly what deliverable (d) asks.** Lines 185-188 of the script: on `--dry-run`, it prints the full request body with `.token` replaced by `"***REDACTED***"` and exits 0, with no `curl` call before that branch. The provenance line (156) is `"[repo:${repo_slug}] via sapience-remember.sh (Claude Code dispatch)"` — the tag is unconditional, not contingent on any flag. The gap is purely in test coverage, not in script behavior.

**Rule-registration mechanism for deliverable (b).** Other extensions (e.g. `nvim`) register a rule via `manifest.json`'s `provides.rules: ["neovim-lua.md"]`, pairing a `rules/<name>.md` file carrying YAML frontmatter `paths: [...]` that the harness auto-loads whenever a touched/referenced path matches the glob (independent of any `@`-import list — confirmed by this repo's own root `.claude/CLAUDE.md`, "Rules References" section's closing paragraph). The sapience extension currently declares `provides.rules: []`. Adding a rule here would need: (1) a new `rules/<name>.md` file with frontmatter scoping it to `agent-system/extensions/sapience/**` (and plausibly `.claude/context/project/sapience/**` post-deploy), (2) a `manifest.json` entry in `provides.rules`, and (3) the rule's own prose stating the standing contract.

**Mechanizing the "prescriptive vs. discussing" distinction is the same problem this codebase has already solved once, with a marker convention.** `scripts/lib/task-reference-patterns.sh` and `scripts/lib/record-version-patterns.sh` (both core extension) use a documented marker convention (`task-ref-ok`, `version-ok`) to let a legitimate, intentional mention suppress an otherwise-correct lint hit. The dispatch's own acceptance criterion 3 flags exactly this risk for a sapience write-path lint: `per-repo-scoping.md` and `review-gate-boundary.md` both legitimately *discuss* all four MCP write tools by name. A naive grep for `sapience_remember|sapience_wrapup|sapience_handoff|sapience_adddoc` would hit both legitimate files. A marker-suppression approach (mirroring the two precedents above) is the only mechanized shape this codebase already has evidence it trusts for this exact false-positive class — but building and wiring a new lint script (plus a CI/test-suite hook) is materially more implementation effort than an advisory rule, for a corpus of exactly 12 files.

**`settings-fragment.json` still grants all four write tools, including two the extension's own text says never to use proactively (`sapience_remember`) or ever (`sapience_wrapup`, replaced).** This is a live design question, not a mechanical finding: keeping the grant means an agent that ignores the prose instruction (or follows the vendor's SessionStart nudge) can still successfully call the tool non-interactively, producing exactly the untagged write this task exists to eliminate. Narrowing the grant (e.g. dropping `sapience_remember` and `sapience_wrapup` from the allow-list, keeping only `sapience_handoff`/`sapience_adddoc` pending their own ruling) would make a stray proactive call fail on an interactive permission prompt in a headless dispatch — a second, mechanical line of defense beyond prose. This is a plan-level tradeoff (see Risks & Mitigations) because `agent-system/extensions/core/context/patterns/mcp-server-ownership.md` cites the *current* four-tool grant as its own worked example for the nix-enforced-settings carve-out (lines ~330-343) — narrowing the sapience grant would leave that cross-extension doc's worked example stale, and `core/` is outside this task's declared edit target.

## Recommendations

1. **Correct the two stale domain files** (`review-gate-boundary.md` lines 24-30/42, `transcript-filter-ceiling.md` line 40) to describe the actual current postflight mechanism (`sapience-remember.sh`, a direct unauthenticated-by-MCP `POST /ingest-kos` call) rather than "call `sapience_wrapup`" / "an explicit MCP tool call." This directly satisfies acceptance criterion 6's `review-gate-boundary.md` half (the `per-repo-scoping.md` half is already correct and needs no change) and removes an internal contradiction that currently exists in the extension's own documentation.

2. **Add an explicit ruling for `sapience_handoff` (and, for completeness, `sapience_adddoc`)** — a short, dedicated statement (candidate location: `EXTENSION.md` itself, or a new subsection of `review-gate-boundary.md`) naming each of the four MCP write tools and stating its disposition: `sapience_remember` → never call proactively, converted writes go through the script; `sapience_wrapup` → replaced, never call; `sapience_handoff` → [ruling needed — likely: session-closing handoff notes are a distinct concern from the postflight knowledge-capture bound and are not currently instructed anywhere, so there is nothing to convert; state this explicitly rather than leaving it to inference]; `sapience_adddoc` → out of scope (document ingestion, not finding capture). This closes the "ruled out and the reason recorded" half of deliverable (a) for the tools that have no current call site.

3. **Add write-side test cases to `scripts/tests/test-sapience-capture.sh`** (or a sibling file, if the plan prefers not to touch the retrieve-focused file's existing 9-case numbering) asserting, via `--dry-run` with no network stub required: (a) exit code 0, (b) `.provenance` contains `[repo:<repo_slug>]` where the slug is derived the same way `sapience-retrieve.sh`'s existing scratch-repo fixture derives it, (c) `.token` is replaced by the literal `"***REDACTED***"`, never the real `SAPIENCE_TOKEN` value. This is deliverable (d), currently fully unmet.

4. **Resolve deliverable (b) as an advisory rule, not a mechanized lint, for this pass** — add a new `rules/sapience-write-path.md` (or fold the contract into a clearly-labeled section of `EXTENSION.md`) with `paths:` frontmatter scoped to `agent-system/extensions/sapience/**`, stating in prose: "no instruction surface in this extension may name an MCP write tool as a prescribed write path; discussing why a tool is not used is permitted." Register it in `manifest.json`'s `provides.rules`. Recommend *against* building a new mechanized lint in this same task: the corpus is 12 files, exactly two of which legitimately discuss the tools by name (already identified above), and a marker-suppression mechanism precise enough to avoid flagging them (mirroring `task-reference-patterns.sh`/`record-version-patterns.sh`) is a disproportionate build for a corpus this small and this static. State this as the explicit tradeoff in the rule's own text so a future reader does not mistake "advisory" for "unconsidered."

5. **Strengthen deliverable (c)'s counter-instruction to name the vendor nudge explicitly**, rather than relying on inference from "write 3-8 notes at postflight" + "don't call proactively" to imply redirection. A concrete, minimal edit: append one sentence to `EXTENSION.md`'s existing prohibition, e.g. "This supersedes the Sapience SessionStart briefing's own standing nudge to save findings with `sapience_remember` immediately — hold any such finding and let it surface through the bounded postflight pass instead." This makes the redirect (not mere suppression) explicit and checkable by inspection, satisfying deliverable (c) and acceptance criterion 5 without any code change (the SessionStart hook itself remains untouched, per the owner-action boundary).

6. **Leave `settings-fragment.json`'s grant unchanged in this pass, and record the tradeoff rather than resolving it**, unless the plan phase explicitly decides narrowing it is in scope. Revoking `sapience_remember`/`sapience_wrapup` from the grant is a real, available "enforced" option for deliverable (b), but it (a) changes existing, working non-interactive-prompt behavior for the whole repo, (b) leaves `core/mcp-server-ownership.md`'s worked example citing a grant that no longer matches, and (c) a stray interactive-session call to `sapience_handoff`/`sapience_adddoc` (not yet ruled out) would also be affected by any blanket narrowing. This is exactly the kind of judgment call `user-decision-contract.md` describes — flag it for the plan/implementation phase rather than deciding it here.

## Risks & Mitigations

- **Risk**: Correcting `review-gate-boundary.md` and `transcript-filter-ceiling.md` without also touching `per-repo-scoping.md` could look inconsistent to a future reader if not done carefully, since all three files discuss the same hazard. **Mitigation**: cross-reference `per-repo-scoping.md`'s already-correct "D3: Why Replace, Not Both" section explicitly from the corrected passages, rather than restating it.
- **Risk**: Adding a new `rules/*.md` file changes `manifest.json`'s `provides.rules` array, which is a deploy-affecting change requiring a redeploy (`deploy-headless.sh`) to take effect, per the dispatch's own instruction. **Mitigation**: this is expected and already named in the dispatch description ("REDEPLOY via deploy-headless.sh") — just confirming it applies to this specific deliverable too, since a rule file is new deploy surface, not an edit to an existing deployed file.
- **Risk**: Narrowing `settings-fragment.json` (if a future pass chooses to) would make `core/mcp-server-ownership.md`'s sapience worked example stale, and that file is outside this task's edit target. **Mitigation**: if/when that narrowing happens, it should be its own follow-up task (or an explicitly `out-of-scope`-flagged edit note) rather than silently drifting that cross-extension doc out of sync — do not attempt it in this task per the stated boundary.
- **Risk**: A mechanized lint for deliverable (b), if attempted despite Recommendation 4's advice against it, risks exactly the false-positive failure mode the dispatch itself warns about (flagging `per-repo-scoping.md`/`review-gate-boundary.md`'s own legitimate discussion). **Mitigation**: if the plan phase overrides Recommendation 4 and still wants mechanization, require a marker-suppression design (mirroring `task-reference-patterns.sh`) from the start, never a bare grep.

**Empirical findings for Phase 4 to carry into documentation** (do not re-derive, cite these):
1. **Byte-identity (requirement c) needed the contingency.** `jq .`'s default behavior is
   order-preserving, not sorting; `M.write_json`/`M.merge_settings` now take an optional
   `opts.sort_keys` (`jq -S .`), passed only from the `mcp` branch. No other caller's output
   format changed.
2. **The regenerate-then-unload risk REPRODUCES.** A `load -> regenerate (forced reload) ->
   unload` sequence does not retract the extension's own entry, because `manager.load`
   OVERWRITES (never merges) the persisted `merged_sections` tracked data on every load call,
   and a reload over already-present content produces a thinned tracked structure. This is a
   pre-existing limitation of the shared `merge_settings`/`state_mod.mark_loaded` path (the
   `settings` branch has the identical limitation) -- not introduced by `mcp`, and out of this
   task's scope to fix. A PLAIN `load -> unload` round trip (no intervening reload) retracts
   fully and correctly, including decision 6's empty-file cleanup.
3. **`claude mcp get <fixture>` resolved the server**, reporting
   `Scope: Project config (shared via .mcp.json)` and
   `Status: ⏸ Pending approval (run \`claude\` to approve)` -- a visible pending-trust status,
   not an outright resolution failure. Phase 4's gotcha documentation should state this exact
   shape rather than a generic "may be invisible" claim.

**What NOT to Try**: Do not attempt to fix the regenerate-then-unload limitation (out of scope,
pre-existing, shared with the `settings` path). Do not add `sort_keys` to any caller besides the
`mcp` branch.

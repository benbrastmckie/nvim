## Findings

### Codebase Patterns

**Existing lint cluster conventions** (`agent-system/extensions/core/scripts/lint/`, 15 scripts, ~6,500 lines total):
- Every lint in the cluster uses a dual-mode root-resolution probe (`resolve_project_root()` walking up from `SCRIPT_DIR` until `agent-system/extensions` is found, falling back to `common_repo_root`), so the same script runs correctly from the source store or a deployed `.claude/` checkout.
- `lint-corpus-scan-lib.sh` (`agent-system/extensions/core/scripts/lib/`) provides two reusable functions sourced by (not copy-pasted into) most of the cluster: `lint_corpus_scan_collect_files OUTVAR DEFAULT_SCAN PATTERN... -- SCAN_PATH...` (file collection, with automatic reuse of `verify-deploy.sh`'s pre-built whole-corpus enumeration when the scan root is unmodified) and `lint_corpus_scan_parse_flags` (the shared `--verbose/--quiet/positional-paths` argument loop). Two of the fifteen existing lints (`lint-task-lookup-adoption.sh`, `lint-hook-registration-paths.sh`) were reasoned exclusions from the file-collection helper because their pattern-matching contracts differ from the flat single-pattern-set shape — this task's lint is a third such case (full-corpus `*.md`+`*.json` scope, not the executable-surface-restricted scope every existing adoption lint shares) and should reuse `lint_corpus_scan_collect_files` for its file-collection layer only, with its own pattern-matching/classification logic, exactly as those two precedents do.
- Exit-code convention is uniform: `0` = clean, `1` = violations found, `2` = environment/usage error.
- `--verbose`/`--quiet` flags are standard; `--verbose` reports every candidate including exempt ones with its exemption reason (per `lint-task-lookup-adoption.sh`).

**`adoption-lint-conventions.md` — binding design doc, with one requirement this lint cannot satisfy as written** (`agent-system/extensions/core/context/patterns/adoption-lint-conventions.md`):
- States two established conventions for a "hand-rolled pattern regrowing" lint: zero-tolerance (single-source assertion, no allowlist) vs. structural-plus-reasoned-allowlist. The decision rule is explicit: "Non-zero migration debt at landing time selects the allowlist convention. A class already migrated to (or starting at) zero selects zero-tolerance."
- States two structural requirements every adoption lint "in this repo must satisfy": (1) dual-mode root resolution (satisfied by reusing the existing probe/library — applies cleanly here), and (2) "Executable-surface file scope by construction... `docs/`, `context/`, and `rules/` are out of scope because the scan never visits them." Requirement (2) is scoped to the "hand-rolled pattern" adoption-lint class this doc documents (where illustrative prose about a code anti-pattern in `context/`/`docs/` is never itself the defect). **This task's lint is a different class**: an actionable recommendation line IS the defect regardless of which directory renders it, and the dispatch's own list of representative core sites (`context/formats/subagent-return.md`, `context/patterns/checkpoint-execution.md`, `context/orchestration/orchestration-reference.md`, `docs/guides/user-guide.md`, `docs/guides/creating-agents.md`, `docs/guides/creating-skills.md`) is mostly `context/`+`docs/` files. The plan should state explicitly that this lint is scoped to the full `agent-system/extensions/**/*.{md,json}` corpus (matching where the 92-file hit set actually lives: 34 files under `agents/`, 21 under `skills/`, 19 under `commands/`, 14 under `context/`, 4 under `docs/`) and is NOT a member of the conventions doc's "adoption lint" class for purposes of requirement (2) — only requirement (1) (dual-mode root resolution) transfers.

**Gate wiring is mandatory, not incidental** (`agent-system/extensions/core/scripts/verify-deploy.sh`, `agent-system/extensions/core/scripts/gate-registry.data`):
- Gates run 1-23 today (confirmed: `grep -n "^gate[0-9]*_run()"` lists `gate1_run` through `gate23_run`, no gaps). Every one of the 15 lint scripts in `scripts/lint/` that is meant to run in CI/deploy verification has a corresponding `gateN_run()` function in `verify-deploy.sh` PLUS a row in `gate-registry.data` (tab-separated: id, description, invoke-fn, `-`, boolean, timeout_s, cost-tier, boolean, scan-path hints). A new lint without a gate row runs standalone only and is never exercised by `verify-deploy.sh`'s battery — the plan must add gate 24 (new `gate24_run()` function, modeled line-for-line on gate 18/21/23's `[SKIP]`-when-not-source-store / `fail`-when-script-missing / `pass`-or-`fail`-plus-`FINDINGS_LIST` shape) and append one `gate-registry.data` row.
- `gate-registry.data`'s own trailing comment states this directly: "adding a migrated gate is a new row here plus a `gateN_run` function definition, not a 40-line copy-pasted if/fi block" — i.e. the row-plus-function pattern is the sanctioned mechanism, already proven by 23 precedents.

**Fixture-test convention** (`agent-system/extensions/core/scripts/tests/test-lint-task-lookup-adoption.sh`, representative):
- `mktemp -d` scratch workdir via `common_test_workdir_init`; `common_test_resolve_candidate` for deploy-tree-first / source-store-fallback script resolution; `common_test_pass`/`common_test_fail`/`common_test_info` helpers; exit `0`/`1`/`2` convention mirrors the lint itself but reports test success, not lint success.
- Explicitly includes a "Case 1 (acceptance criterion)" planting a synthetic *new* offender and asserting the lint fails with the exact `file:line` named — this is the pattern the dispatch's "deliberately-violating fixture that proves the lint fires" requirement maps onto directly.
- `agent-system/extensions/core/scripts/tests/run-all.sh` auto-discovers suites via a glob (`for f in "$ext_scripts/tests"/test-*.sh`) per extension, confirmed by direct read (lines ~274-312) — **no central registration list exists**; dropping a correctly-named file under `agent-system/extensions/core/scripts/tests/` is sufficient for it to run under gate 8 (the whole shell-test-suite-runner gate) automatically.

**Valid-command enumeration — verified exact mechanics**:
- `find agent-system/extensions/*/commands -maxdepth 1 -name "*.md"` yields 47 unique basenames; the one non-command file is `agent-system/extensions/core/commands/README.md`. Excluding basename `README` (case-sensitive match on this repo's one instance; case-insensitive exclusion is the safer general rule since nothing else guarantees a future README stays uppercase) yields exactly 46 names, matching the dispatch's enumerated list verbatim: `analyze approve book books budget certify cite consult convert deck distill edit email epi errors finance fix-it funds grant lake lean learn legal literature market meeting merge meta orchestrate please pr project project-overview refresh review revise scrape sheet slides spawn strategy table tag task timeline todo vet zulip`.
- No existing script already performs this enumeration as a reusable function; it is new logic for the new lint, straightforward to implement as `find "$EXT_ROOT"/*/commands -maxdepth 1 -name '*.md' ! -iname 'readme.md' -printf '%f\n' | sed 's/\.md$//' | sort -u` or an equivalent loop.

## Recommendations

1. **Lint design**: structural classifier (regex matching a literal `Next: /X` or `Run: /X`-shaped recommendation line, case-sensitive on the leading keyword, tolerant of backticks/markdown emphasis around the command name) + a valid-command set built by enumerating `agent-system/extensions/*/commands/*.md` basenames (excluding `README.md`, case-insensitively) at lint run time — exactly as the dispatch specifies, with no hardcoded allowlist of command names. A line naming a command NOT in that set is a finding.
2. **Scope**: full `agent-system/extensions/**/*.md` + `agent-system/extensions/**/*.json` corpus (reuse `lint_corpus_scan_collect_files` for file collection with these two patterns and a default scan root of `$REPO_ROOT/agent-system/extensions`, enabling the shared-corpus fast path for free). Do **not** restrict to `commands/`, `skills/`, `agents/` the way the adoption-lint-conventions.md structural requirement (2) prescribes for the hand-rolled-pattern lint class — this lint is a different class (see Findings above) and under-scoping it would miss the `context/`+`docs/` sites the dispatch explicitly names as in-scope (17 of 92 hit files).
3. **Convention choice**: zero-tolerance, no allowlist, once the task completes — justified by `adoption-lint-conventions.md`'s own decision rule (debt retired to zero within the same landing event selects zero-tolerance, not allowlist-with-incremental-retirement). Sequence: write the lint first (expected red, ~187-188 findings, serving as the enumerator/worklist), fix every sub-class A site across all 12 extensions, then commit the lint with zero exceptions. Do not land the lint pre-wired into gate 24 while it is still red — per `no uncommitted/partial work` and `commit-per-green-substep` conventions, the gate-registry row and `gateN_run()` addition should land in the same (final) phase that confirms the lint is green, not earlier.
4. **Sub-class B fix**: edit `agent-system/extensions/core/context/formats/command-output.md` directly — delete or remap the `/research`/`/plan` entries out of Template A's "Assigned Commands" line and the Template Assignment Table, and the `/implement` entry out of Template B's "Assigned Commands" line and table row (keeping `/task`, `/revise`, `/errors`, which are real commands). No other file needs updating as a consequence: the two files that reference `command-output.md` (`index-entries.json`, `context/standards/interactive-selection.md`) do so by cross-reference/prose only, confirmed by direct grep — neither parses the Assigned-Commands lines or table programmatically. Note for the plan's judgment call, not pre-decided here: `/orchestrate` itself is not currently assigned to any template at all (only appears in `Next:` example lines, never in an "Assigned Commands" list), which the plan may choose to address as part of the structural remap (adding `/orchestrate` to Template A) or leave as a separate, explicitly-deferred decision — this is prose/structural judgment the dispatch assigns to this task's plan, not a mechanical fact.
5. **Gate wiring**: add `gate24_run()` to `verify-deploy.sh` modeled on gate 18/21/23's exact shape (`[SKIP]` when `$TARGET/agent-system/extensions` doesn't exist, `fail` when the lint script is missing, `pass`/`fail` plus `FINDINGS_LIST` population keyed on the lint's own `[VIOLATION]`-tagged output lines) and one new tab-separated row in `gate-registry.data` (id 24, description, `gate24_run`, cost tier `free` given the lint's expected low runtime, scan-path hint `@extensions`).
6. **Fixture suite**: `agent-system/extensions/core/scripts/tests/test-lint-<name>.sh`, modeled on `test-lint-task-lookup-adoption.sh`'s structure (`mktemp` workdir, `common_test_resolve_candidate`, at minimum: Case 1 a synthetic NEW offender naming a nonexistent command and asserting non-zero exit + `file:line` in output; Case 2 a synthetic line naming a REAL command (e.g. `/orchestrate`) in the same shape and asserting it is NOT flagged — proving the valid-command enumeration, not just the regex, drives the verdict). No run-all.sh registration needed; glob auto-discovery picks it up.

## Decisions

- This lint is treated as outside the `adoption-lint-conventions.md` "hand-rolled pattern" class for purposes of its file-scope structural requirement; only that doc's dual-mode-root-resolution requirement and its allowlist-vs-zero-tolerance decision rule transfer. Full corpus scope (`*.md`, `*.json` across all of `agent-system/extensions/`) is required to cover the dispatch's named sites.
- Zero-tolerance (no allowlist) is the correct convention for this lint, per `adoption-lint-conventions.md`'s own decision rule, because this task retires all sub-class A debt before the lint lands in its gated form.
- `lint-routing-wiring.sh` and `lint-contract-compliance.sh` are confirmed, by direct source reading (not just the dispatch's prior claim), to be non-natural hosts; `lint-routing-wiring.sh` is the closer conceptual peer but still does not enumerate `commands/*.md` and has a different jq-based, manifest-keyed detection model incompatible with this lint's line-oriented, full-corpus-text detection model. A new file in `scripts/lint/` is warranted.
- Sub-class B's fix is confined to one file (`command-output.md`); no downstream consumer requires a coordinated edit.

## Risks & Mitigations

- **Risk**: a naive regex for "Next: /X" / "Run /X {N}" may over- or under-match relative to the dispatch's exact 187 count (this research's independent grep found ~188 using a looser pattern, and found at least one non-recommendation false-positive-adjacent hit, `deck-builder-agent.md:529: "Run /plan first."`, which IS an actionable recommendation naming a dead command and should legitimately count, plus `analyze-agent.md:330`'s `next_steps` JSON-string form, a different literal shape (`"Run /plan to create..."` inside a JSON value) worth confirming the lint's regex also catches). *Mitigation*: the plan/implementation phase should design the regex against the dispatch's own worked examples first, run it, and treat any count different from 187 as a cue to re-examine false positives/negatives rather than assuming the dispatch's figure is exactly reproducible by a different regex dialect — the two counts need not match line-for-line as long as both enumerate the same underlying defect class.
- **Risk**: scanning `*.json` broadly (not just the one known `errors-schema.json` hit) could pick up unrelated JSON containing the literal substring `/plan` or `/implement` in an unrelated context (e.g. a filesystem path). *Mitigation*: anchor the regex on the `Next:`/`Run`-prefixed recommendation shape (as the dispatch specifies), not a bare command-name substring match — this already excludes most incidental path-like occurrences.
- **Risk**: adding gate 24 while other tasks are concurrently touching `verify-deploy.sh`/`gate-registry.data` (both are shared, contended files per the batch-orchestration-guardrails convention). *Mitigation*: the plan should treat these two files as their own narrow commit scope, consistent with `git-staging-scope.md`'s per-operation contract, and check for concurrent dispatches touching them before editing.

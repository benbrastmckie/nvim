## Key Decisions Made

- **Grammar**: a comma-separated list of entries, or the bare placeholder `-`. Each entry is one
  of `@extensions` (the existing `gate_registry_shared_corpus_build` producer, reused not
  re-walked), `@repo` (a NEW named view, not yet backed by a resolver -- reserved for gates 4 and
  22, which are genuinely repo-wide), a literal path, a bare directory (recursive prefix match),
  a glob, or any of those `!`-prefixed for exclusion (e.g. `@repo,!specs/**`). Resolution order
  (for Phase 3 to implement): union every non-`!` entry, then subtract every `!`-prefixed one.
- **Risk-calibrated declaration confidence**: gates whose cost class makes skip-caching actually
  matter (3, 4, 6, 8, 10, 12, 17, 21, 22, 23, and the broad source-store lints) got a confident
  declaration from reading the gate function body directly. Gate 14 (free class, genuine
  uncertainty about its exact read set) was declared `-` rather than guessed -- safe default,
  since skipping an already-near-free gate buys nothing anyway. This principle is recorded in
  `progress/phase-2-corpus-declarations.md`'s own preamble for whoever extends this table later.
- **`@extensions,.claude` for gates 5 and 13**: both gates compare the source store AGAINST the
  deployed tree (opposite directions of the same comparison -- gate 5 declared-vs-deployed, gate
  13 deployed-vs-declared), so both legitimately need both sides in their corpus, not just one.
- **Field-count check (lint Check F) is a SECOND pass over the raw file**, not inferred from what
  `read` populated on the first pass -- a short row just leaves trailing bash variables
  empty/unset rather than signalling a parse failure on its own, so this counts each row's own
  tab characters directly via `awk -F'\t' '{print NF-1}'`.

## What NOT to Try

- Do not attempt `git stash` push/pop for a quick before/after diff in this repo while other
  sessions may be active -- the stash is a single shared stack ref per repo, and
  `guard-destructive-git.sh` will refuse a chained push+pop command outright rather than risk
  dropping a foreign entry. Use a different diffing strategy (a worktree, or accept structural
  evidence) if a future phase needs a true before/after comparison.
- Do not assume the registry's `input_corpus` field is resolved or consumed anywhere yet -- it is
  purely declarative as of this phase. A future phase (3+) implementing the resolver is the first
  real consumer; until then, `gate_registry_field N input_corpus` only echoes the raw declared
  string.

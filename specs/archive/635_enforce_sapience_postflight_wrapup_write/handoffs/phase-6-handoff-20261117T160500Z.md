## Deviations from Plan

- **Gate-8 incident** (recorded via `issue-record.sh`, class `gate collision`, severity
  `costly`): including gate 8 in the `--only-gate` list triggered `verify-deploy.sh`'s own
  internal UNFLAGGED full `run-all.sh` sweep (all 203 suites) under the `specs/.gate-lock`
  mutex — exactly the full-sweep/contention cost the Batch Gate Deferral directive exists to
  prevent. The run stalled 580s+ with no progress. Recovered by killing the run and its
  already-dispatched job-worker children (reparented to systemd, operating against throwaway
  `/tmp` fixtures, self-terminating harmlessly), releasing the stale `specs/.gate-lock` entry
  via `task-lock.sh gate-release <token>` (the sanctioned release path `verify-deploy.sh` itself
  uses), and re-running `--only-gate 3,4,5,22,29` (excluding 8) — 6/6 PASS in seconds. Gate 8's
  own content was already covered, gate-lock-free, by the earlier suite-scoped `run-all.sh`
  run. **Lesson for a future dispatch under the same directive: never include gate 8 in an
  `--only-gate` list; its content is covered by the separate `run-all.sh --only SUITE[,...]`
  narrowing invocation instead.**

## What NOT to Try

- Do not include gate 8 in a `verify-deploy.sh --only-gate` list under a Batch Gate Deferral
  directive — see the incident above. Use `run-all.sh --only SUITE[,...]` for suite-level
  coverage instead; it does not touch `specs/.gate-lock` for a narrowed run.

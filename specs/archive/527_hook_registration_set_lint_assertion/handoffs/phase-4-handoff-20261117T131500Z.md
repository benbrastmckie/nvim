**Key Decisions Made**:
- **A real pre-landing defect was caught and fixed in this phase**, in Phase 2/3's own code (not
  new Phase-4 code): Check E's `DEPLOYED_SETTINGS` default unconditionally pointed at the REAL
  live `.claude/settings.json`. Every pre-existing Check-A-D fixture case passes its OWN narrow
  custom scan path (to isolate Checks A-D), which also narrows Check E's declared set to nearly
  nothing -- so Check E would have spuriously flagged dozens of real registrations in the real
  deployed tree for cases that have nothing to do with Check E, breaking every PASSING-polarity
  pre-existing case the moment the deployed copy eventually carries Check E (post-Phase-6-
  redeploy). Fixed in `lint-hook-registration-paths.sh` by capturing `SCAN_PATH_GIVEN` right after
  flag parsing (before the default-scan fill) and withholding the `DEPLOYED_SETTINGS` default
  entirely whenever an explicit scan path was given without an explicit `--deployed-settings`/env
  override -- Check E then sees zero deployed rows, exactly like the missing-file degrade. Logged
  via `issue-record.sh` (class: design defect caught before landing). Re-verified byte-identical
  default-path output after the fix.
- Fixture provenance for the three shape cases: case 19 embeds ModelBuilder's real
  `.claude/settings.json` verbatim (companion `hooks/` planted with the 3 undeclared-but-present
  scripts); case 20 embeds Logos/Theory's real, clean file verbatim plus the plan's one documented
  mutation (a second `Notification` matcher block), with a companion `hooks/tts-notify.sh`; case 21
  embeds SPSDemo's real file verbatim with a companion `hooks/` directory planting its other 19
  real hook names but never `scripts/claude-ready-signal.sh`.
- Cases 22/24/25 use a minimal custom empty-scan-path directory alongside `--deployed-settings`,
  rather than the full default source scan, since their assertions don't depend on the real
  declared set and a minimal scan is faster and fully deterministic.

**Deviations from Plan**: One verification-reporting caveat, not a deviation in substance: the
suite's DEFAULT (`deploy-tree-first`) subject resolution will continue to show cases 19-25 as
failing (`ERROR: scan path not found: --deployed-settings`, from the stale deployed copy that
predates Check E) until Phase 6's redeploy syncs the deployed copy -- this is the suite's own
documented, intentional pre/post-redeploy divergence signal (`common_test_resolve_subject`'s own
header comment), not a defect. `CORE_TEST_SUBJECT_MODE=source-store` is the correct verification
mode for this phase, pre-redeploy. The same divergence makes `run-all.sh`'s five-suite tier list
`test-lint-hook-registration-paths.sh` as a third failure alongside the two already-logged
unrelated/EXPECTED ones (`test-deploy-baseline-lib.sh`, `test-verify-deploy-context-budget.sh`);
all three resolve, for their respective reasons, once Phase 6 redeploys and runs the complete
gate set.

**What NOT to Try**: Do not "fix" the default-mode suite failure by hardcoding
`CORE_TEST_SUBJECT_MODE` inside the test file -- that would defeat the pre/post-redeploy
divergence signal the mode exists to preserve. Do not revert the `SCAN_PATH_GIVEN` fix to simplify
the code; it closes a genuine defect, not a cosmetic one.

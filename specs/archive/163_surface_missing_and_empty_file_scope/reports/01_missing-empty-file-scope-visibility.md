### Codebase Patterns

#### `validate-state.sh` today (Check 8 / Check 9)

- Check 8 (`agent-system/extensions/core/scripts/validate-state.sh:460-499`): flags a *coarse, directory-shaped* `file_scope` entry (trailing slash) that overlaps ≥3 (configurable via `FILE_SCOPE_COARSE_MIN_OVERLAP`) other non-terminal tasks, using `scopes_overlap_first` spliced from `lib/file-scope-overlap.sh`'s `FILE_SCOPE_OVERLAP_JQ_DEFS`. Iterates `(\$task.file_scope // [])[]` — an absent or null `file_scope` yields the empty array, so zero entries are ever produced or checked for that task. WARN-only, unconditionally (no `--strict` path exists yet).
- Check 9 (`:501-539`): flags duplicate entries *within* one task's own `file_scope` array — Class A (exact duplicate, `--fix`-repairable) and Class B (normalization-equivalent, e.g. `"a/"` vs `"a"`, never auto-repaired). Same `// []` default means an absent/null array produces zero duplicate pairs, never a finding.
- Both checks operate over **non-terminal** tasks only (`status` not in `{completed, abandoned, expanded}`), matching the definition already used by `is_terminal` in Check 8's jq program. The new checks should use the same non-terminal filter to stay consistent with the existing WARN family and with the "active tasks" framing in the dispatch's own measurement claim.
- `--fix` (lines 208-283) repairs **only** Check 9 Class A (exact duplicates); it explicitly never touches Class B, and it is gated behind `if has("file_scope") then ... else . end` so it never manufactures a `file_scope: []` field on a task that never had one (confirmed at lines 253-255's own comment). This is the existing behavior the new checks must not disturb — no code path in `validate-state.sh` today would auto-repair an absent key into `[]`, so satisfying the dispatch's "`--repair` does not manufacture `[]` on absent keys" acceptance line requires no *change*, only a verification that no new `--fix` branch is added for the new checks (or, if one is added, that it is scoped away from absent keys exactly as Check 9's `--fix` already is from Class B).
- `validate-state.sh` has **no `--strict` flag today** — every WARN-only check (8, 9, and the two new ones) is permanently non-blocking regardless of invocation flags. If the plan wants "‑‑strict enforces it today" parity with `validate-artifact.sh`, a new `--strict` flag must be added to this script (argument parsing at lines ~120-145, plus a `total_issues=$((errors+warnings))` style branch before the final exit).

- Class B (`:256-264`) is explicitly literal-null-only, by design, per its own comment: *"A genuinely absent key is NOT flagged — only a present-but-literal-null value is the anomaly this class exists to surface."* This is a deliberate, documented non-goal, not an oversight — confirming the dispatch's framing.

#### The glob story: Overlap vs. Containment (load-bearing distinction)

`context/patterns/file-footprint-overlap.md` (canonical algorithm doc, referenced by both target scripts) defines **two separate predicates**, not one:

1. **Overlap** (`scopes_overlap_first` / `scopes_overlap()`) — symmetric, used by Check 8, Class C, Class D, Class E, and the multi-task-creation collision check. Its own **Non-Goals** section states explicitly: *"No glob or regex matching in the symmetric Overlap Rule (e.g. `*.lua`, `**/test_*`) — only literal directory-prefix containment between two scopes. ... This is a deliberate design decision."* A glob-shaped entry genuinely never collides with anything under this predicate — this is the real, confirmed mechanism behind the addendum's observation (`*/agents/**` colliding with nothing despite three tasks editing agent files).
2. **Containment** (`path_covered_by_scope()`, `lib/file-scope-overlap.sh:159-201`) — one-directional, used by `git-snapshot.sh`'s per-dirty-path scope-restriction loop. Its clause 3 is an *additive, deliberate* glob-matching extension, justified in the doc by an observed historical population of glob-shaped entries ("3 of 249") that would otherwise never be recognized as covering anything. This predicate already works correctly for glob entries today.
3. `orchestrate-cycle-plan.sh`'s `_sibling_territory_classify_entry()` (`:1974-1983`) already has a first-class `"glob"` granularity label (`case "$path" in *[*?\[]*) echo "glob" ...`), used to build the `entries[].granularity` field seen live in **this task's own dispatch file's Territory JSON** (task 43 and task 207 are rendered with `"granularity":"directory"` and a "may touch any file within it" note by this exact mechanism — the same code path would render `"granularity":"glob"` identically if a glob-shaped entry existed live, but none currently does — confirmed 0 glob-shaped entries in this repo's live `active_projects[]`).
4. That same comment block (`orchestrate-cycle-plan.sh:1943-1947`, "Decision 4") explicitly **defers** the question of whether an absent/coarse/glob `file_scope` should affect admission to "the separate, already-filed work scoped to `orchestrate-batch-admit.sh`'s own admission gate" — this task (163) is very plausibly (part of) that deferred work, at least for the *visibility* half of the problem (this task is scoped to detection/reporting, not to changing admission behavior in `orchestrate-batch-admit.sh` itself, which is out of the stated file_scope for this task).

**Conclusion for the plan phase**: a glob entry should be surfaced as *"this entry will never be compared by the Overlap-based checks (Check 8, Class C/D/E) — if you need collision detection to see it, declare a directory or file entry instead,"* not *"glob syntax is invalid/forbidden."* Wording it as an outright rejection would misrepresent the codebase's own documented design (the Non-Goals section) and would conflict with the already-working Containment consumer. The measurement claim of "0 glob entries exist in the live file" is confirmed accurate for this repo's current non-terminal `active_projects[]` (checked directly); `specs/archive/state.json` (terminal/archived tasks, out of scope for these WARN-only non-terminal checks) does contain 10 glob-shaped historical entries, which is consistent with — and slightly refines — `file-footprint-overlap.md`'s cited historical "3 of 249" figure (likely stale itself, or scoped to a narrower snapshot).

#### Reusable glob-detection idiom

The identical bash case pattern for "does this string contain a glob metacharacter" already exists twice, independently transcribed:
- `lib/file-scope-overlap.sh:190` (`path_covered_by_scope`): `case "$norm_entry" in *[\*\?\[]*) ...`
- `orchestrate-cycle-plan.sh:1978` (`_sibling_territory_classify_entry`): `case "$path" in *[*?\[]*) echo "glob"; return ;;`

Both new checks (in `validate-state.sh` and `orchestrate-predispatch-review.sh`) are jq-based, not bash-based (matching Check 8/9's and Class A-E's own existing shape), so the natural move is a **jq** equivalent, e.g. `def is_glob_entry: test("[*?\\[]")`, added to the shared `FILE_SCOPE_OVERLAP_JQ_DEFS` block in `lib/file-scope-overlap.sh` (both target scripts already splice this variable in) — reusing the exact same character class (`*`, `?`, `[`) as the two existing bash transcriptions, so the three forms never silently diverge on what counts as "glob-shaped." This avoids a fourth independent transcription of the same test.

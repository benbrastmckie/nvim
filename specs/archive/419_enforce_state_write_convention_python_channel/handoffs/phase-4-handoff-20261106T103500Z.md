**Key Decisions Made**:
- The hook scans `$COMMAND` line-by-line (`while IFS= read -r line; do ... done <<< "$COMMAND"`)
  against the SAME `STATE_WRITER_PY_CANDIDATE_LIMB` / `state_writer_py_classify_line` the lint
  uses, so a command allowed by one is allowed by the other and vice versa -- no drift between
  the two consumers' verdicts.
- Blocks via plain `exit 2` + stderr (never `permissionDecision: deny`), per
  `guard-destructive-git.sh`'s documented rationale for Bash-tool hooks.
- Fails OPEN (`exit 0`) on a missing or unsourceable library -- opposite polarity from gate 12,
  which fails LOUD (`exit 2`) on the same condition, since a silently-skipped lint would ship
  unenforced while a silently-failed-open hook merely narrows this one call's coverage.

**Deviations from Plan**: None.

**What NOT to Try**: Do not test the lint's EXCLUDED_FILES allowlist resolution with a
cwd-relative explicit path argument from inside `agent-system/extensions/core/` -- the
allowlist's suffix match is against the full `agent-system/extensions/core/...` prefix, so a
bare relative path like `scripts/tests/foo.sh` will NOT match and will appear to "leak" past the
allowlist. Use an absolute path, or the no-argument default-scan form, when spot-checking
allowlist behavior manually.

**Critical Context**: The hook file's own text does NOT trip the lint (confirmed directly); only
the test suite's deliberate fixture strings do, which is why only
`test-validate-no-python-state-write.sh` (not the hook itself) needed an `EXCLUDED_FILES` entry.

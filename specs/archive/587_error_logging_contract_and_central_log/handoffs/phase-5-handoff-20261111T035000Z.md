## Key Decisions Made

- Captured curl's own `-S` stderr via a scratch `mktemp` file rather than `2>&1`-merging into the
  body capture, to keep body parsing unambiguous even on a transport failure where curl's own
  diagnostic text could otherwise collide with JSON parsing.
- `orchestrate-build-dispatch.sh`'s capture uses the same scratch-file-for-stderr technique,
  guarded so a `mktemp` failure degrades to `/dev/null` (losing only the diagnostic text, never
  failing the dispatch).

## What NOT to Try

- Do not run `test-sapience-capture.sh` or `test-orchestrate-build-dispatch.sh` directly in this
  environment and trust a result at face value without checking `common_test_resolve_subject`'s
  resolution MODE for the subject under test first: `test-sapience-capture.sh` uses
  `"deploy-tree-first"` (so it picks up the stale deployed copy and needs the temp-swap
  technique to exercise the real edit), while `test-orchestrate-build-dispatch.sh` uses
  `"source-store"` for its main SUT (so it exercises the edited source directly, no swap
  needed). The two suites are NOT interchangeable in this respect.
- Do not add a network-initiating health probe or any new call that touches the success path's
  latency -- the whole design here is zero added cost on success; the status is read from the
  SAME request via `--write-out`.

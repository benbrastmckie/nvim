## Key Decisions Made

- `central_log_promote`'s fixed two-argument signature resolves the writing repository's root by
  self-location (its own `BASH_SOURCE`, via `common_repo_root` levels=3) rather than reading a
  caller-supplied `$PROJECT_ROOT` global. This keeps the function correct regardless of what the
  caller's shell state happens to be, and makes it independently testable (the test suite sources
  it directly without going through `issue-record.sh`/`events-append.sh` at all).
- Resolves the owning repository from the FIRST extension entry in `.claude-extensions.json`
  whose `source_dir` resolves to a git toplevel, on the documented assumption that every
  extension in one `.claude-extensions.json` shares a single owning repository (one source
  store). Does not cross-check remaining entries.

## What NOT to Try

- Do not run `bash .claude/scripts/init-specs.sh` to regenerate `specs/.gitignore` before Phase
  7's redeploy — it sources the DEPLOYED (stale, pre-edit) `runtime-file-patterns.sh` and would
  silently regenerate the block WITHOUT the new `central-errors-lock` pattern, undoing this
  phase's own edit. Worked around this phase by sourcing the SOURCE-STORE's edited
  `runtime-file-patterns.sh` directly and splicing its `runtime_specs_ignore_block()` output
  between the existing sentinel markers by hand — confirmed byte-identical to what
  `init-specs.sh` will emit once deployed. Recorded via `issue-record.sh`.
- Do not expect `bash .claude/scripts/check-runtime-file-tracking.sh` or
  `bash .claude/scripts/verify-deploy.sh` (full gate set) to show the new `central-errors-lock`
  pattern before Phase 7's redeploy — both read the deployed tree. `check-runtime-file-tracking.sh`
  was run this phase and PASSED, but only because it is still checking against the pre-edit
  25-minus-1-member deployed copy; it is not yet proof the new member is wired end to end. That
  proof is Phase 7's job.
- Do not literally mention `deploy-headless.sh`, `verify-deploy.sh`, or `run-all.sh` by name
  inside a `unit`-classified test suite's own comments — `lint-unit-integration-boundary.sh`
  greps suite CONTENT textually (not just actual invocations), so a suite classified `unit` that
  merely NAMES one of those three tools in a comment trips the same violation a real invocation
  would. Hit this once in this phase's own test file and reworded the comment to describe the
  constraint without naming the tools.

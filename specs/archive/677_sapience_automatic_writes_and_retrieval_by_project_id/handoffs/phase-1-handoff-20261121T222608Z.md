## Key Decisions Made

- Resolved the API_LIB test subject via `common_test_resolve_subject` (not a hand-rolled
  deploy/source if-elif, which `test-sapience-publish.sh` uses but which does NOT honor
  `CORE_TEST_SUBJECT_MODE`). This repo's sapience extension deploy is currently stale relative

  before switching to `common_test_resolve_subject`.
- Named the new unit-case helper `resolver_write_binding` (not `write_binding`) to avoid
  colliding with Phase 2's own planned `write_binding` helper addition to this same test file.
- The "four-key / token-shaped-key object (refused)" case is satisfied structurally by the
  exact-three-key check alone (no separate key-name-pattern check was added) — any object with a
  4th key, token-shaped or not, already fails the exact-three-key gate.

## What NOT to Try

- Do not resolve `sapience-api-lib.sh` (or any sapience script) as a test subject via a
  hand-rolled `if [ -f deployed ]; then ... elif [ -f source ]; then ...` block when the
  intent is to honor `CORE_TEST_SUBJECT_MODE` — it silently ignores that env var. Use
  `common_test_resolve_subject "<desc>" "deploy-tree-first" "<deployed>" "<source>"` instead.
- Do not run `.claude/scripts/verify-touched.sh` (or any full/scoped gate battery) for a phase
  that declares `**Verification Tier**: local` — the dispatch's Batch Gate Deferral directive
  only applies to phases declaring `full` (Phase 5 in this plan). Running it anyway wastes time
  and, under a concurrent multi-task batch, risks contending on `specs/.gate-lock`.

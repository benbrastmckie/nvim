## Key Decisions Made

1. **Mechanical transform via a Python line-based bash-block-depth tracker**, not hand-editing
   each of the 15 gate blocks. The depth tracker increments on `if ...; then` / `for|while ...;
   do` / `case ... in` (end-of-line anchored) and decrements on a LEADING-WORD match for
   `fi`/`done`/`esac` (`^fi\b`, not `== 'fi'` exactly) — the first version used exact-equality
   matching and silently mis-balanced on `done < <(...)` lines (trailing redirection text after
   the bare `done` token). If Phase 7's scheduler work needs a similar mechanical transform
   again, reuse this corrected matching rule rather than re-deriving it.

2. **`--max-cost` resolution lives in `verify-deploy.sh`, not `gate-registry-lib.sh`.** The lib
   stays the thin interpreter its own header mandates (look up a function, call it); cost-class
   *selection* is a caller-side concern over the already-loaded registry data, resolved once
   right after the argument-parsing `while` loop closes (so it can see `gate_registry_ids`/
   `gate_registry_field`, already loaded earlier in the script, and so it can intersect against
   `--only-gate`'s `GATES_FILTER` regardless of which flag appeared first on the command line).
   An empty intersection sets the sentinel `GATES_FILTER="0"` (no real gate id is ever 0) rather
   than falling back to `GATES_FILTER=""`, which would mean "all gates" — the OPPOSITE of what an
   empty cost-filtered selection should mean. If Phase 7 or later touches `GATES_FILTER`
   semantics, preserve this sentinel distinction.

3. **A full-battery before/after byte-diff against a pre-task baseline is NOT the right
   verification instrument mid-task**, and the plan's own Phase 5 task-7 checklist line now
   carries a completion note explaining why: gates 3/5 (manifest-driven content-drift /
   `provides.scripts` checks) legitimately accumulate NEW findings every phase since Phase 1,
   because the deployed `.claude/` tree has not been redeployed since before Phase 1 started —
   that redeploy is explicitly Phase 11's job, not this phase's. Comparing a fresh capture
   against ANY earlier phase's capture will always show drift growth that is not a regression.
   The clean, meaningful comparison for THIS phase's own transformation was a scoped
   `--only-gate 9-23` before/after (gates 3/5 are both in 1-8, outside that range, so this
   comparison is immune to deploy drift) — confirmed byte-identical stdout AND stderr, both
   sides rc=1 (gate20's one known pre-existing failure). A full-battery capture was still taken
   once (not diffed against a stale baseline) and every `FAIL`/`FINDING` line in it was
   individually root-caused — see below.

4. **Full-battery FAIL root-cause map** (so a future phase doesn't re-investigate these from
   scratch): the full battery currently reports 5 of 37 checks failed. Three are the dispatch's
   own documented pre-existing failures (gate3 lean4 doc-lint missing index.json entry; gate20
   eager-load ~988B over baseline; 3 of gate8's suites: test-detect-noop-bash.sh,
   test-four-tier-conflict.sh, test-guard-git-push.sh). The gate3/gate5 "content
   differs"/"not in provides.scripts" findings are expected pre-redeploy drift (point 3 above).
   Two ADDITIONAL gate8 suite failures appear beyond the documented three —
   `test-deploy-verify-wiring.sh` (invokes the STALE *deployed* `.claude/scripts/verify-deploy.sh`
   copy, untouched by any source-store edit today, so this is pure deploy-lag, not a logic
   regression) and `test-verify-deploy-context-budget.sh` (its own fixture precondition check
   explicitly fails with "baseline fixture is not clean... could not compute a safe eager-load
   pad amount" — a direct, already-logged consequence of the SAME known gate20
   eager-load-over-baseline issue, not a new cause). Neither is a Phase 5 regression. Re-check
   this map after Phase 11's redeploy — most of it should clear, and anything that doesn't
   deserves fresh investigation at that point rather than being waved through again on the
   strength of this note.

## Key Decisions Made

1. **A naive "source each id's dump in sequence" reconciliation is WRONG for concurrently-forked
   ids and was caught live via a smoke test** (CHECKS collapsed from an expected 6 to 1 across 6
   synthetic concurrent gates). Every concurrently-forked subshell's dump is "shared snapshot +
   own delta," not a running total; sourcing them in sequence REPLACES rather than ACCUMULATES.
   Fixed with `_greg_snapshot_vars`/`_greg_apply_delta`: snapshot the real vars once per
   dispatched group (each serialized id's own one-job group; each wave's whole pool), then apply
   each id's DELTA against that shared snapshot (sum for a numeric scalar, append-new-tail-
   elements for an array via a `declare -p`-and-sed-rename-then-source trick, last-write-wins for
   a non-numeric scalar like `CURRENT_GATE`).
2. **A REAL bug in that same fix**: `_greg_snapshot_vars` reset its two scratch associative
   arrays via a bare `NAME=()`. `gate_registry_exec_concurrent_batch`'s own cleanup `unset`s both
   maps after every call (so a later invocation never sees stale data) — but `unset` on a
   `declare -gA` variable destroys its TYPE along with its value, so a SECOND call's bare
   `NAME=()` silently recreated them as ordinary INDEXED arrays. A later string-keyed assignment
   then evaluated the key ARITHMETICALLY, and once the real array already held a hyphenated
   element (`finding-1`), bash's arithmetic evaluator parsed that as a subtraction and choked on
   the unset bare identifier before the hyphen — producing a crash ("finding: unbound variable")
   with no apparent connection to the real defect. Fixed by reasserting `declare -gA` on every
   reset. **If any future function resets a global associative array that something else
   `unset`s between calls, reassert `-A` explicitly — never a bare `NAME=()`.**
3. **A second REAL, intermittent (~1-in-10 to 1-in-15) scheduler bug**: the worker-cap dispatch
   loop's longest-first sort used `mapfile -t ... < <(... | sort | awk ...)`; that process
   substitution's own background reader could still be unwaited in bash's job table when the
   dispatch loop's first `wait -n` ran, occasionally letting `wait -n` reap the reader instead of
   one of the loop's own backgrounded pool jobs — decrementing the active-worker count with no
   real job finished, letting one EXTRA job launch past the declared cap (reproduced directly: 6
   synthetic jobs at cap 2 occasionally ran 3 concurrently). Fixed with a bare `wait` immediately
   after the sort pipeline, before the dispatch loop begins. **Any future `mapfile < <(pipeline)`
   -then-dispatch worker pool should drain the pipeline with a bare `wait` first, for the
   identical reason.**
4. **A naive, non-atomic read-modify-write test counter can only ever UNDER-count a real cap
   violation, never fabricate one** — it masked bug 3 above for several initial test runs. The
   fix was to use `flock`-guarded atomic increments for the test's own verification counter,
   cross-checked against real start/end timestamp overlap (the same technique already used for
   the serialized-isolation case). Any future concurrency test asserting "cap N was never
   exceeded" should use this flock-guarded shape, not a bare counter file.
5. **`--jobs` defaults to `auto`, not `1`** — a deliberate choice (not forced by the plan's own
   wording, which only required "a worker-count flag and its default"): the dispatch's own
   EFFICIENCY goal ("Introduce gate-level concurrency... so independent read-only lints run
   concurrently instead of in series") would not materialize for an ordinary caller if left
   opt-in. `--jobs 1` remains the explicit, byte-identical sequential opt-out.
6. **Measured real speedup**: `--max-cost moderate` (free+moderate gates) went from ~70s
   (`--jobs 1`) to ~43s (`--jobs 4`, the auto-resolved default on this 24-core host) with
   byte-identical output. A full, unscoped battery run (`--findings`, auto jobs) completed in
   790s (13.2 min) — see Verification below for the full finding-set comparison against Phase 6's
   documented baseline.

## What NOT to Try

- Do not source a concurrently-forked gate's `declare -p` dump directly into the real
  CHECKS/FAILURES/FINDINGS_LIST/CURRENT_GATE globals as a bare `source` — see Key Decision 1.
  Every such dump is relative to a shared baseline, not a running total.
- Do not reset a global associative array that gets `unset` elsewhere via a bare `NAME=()` —
  see Key Decision 2. Always `declare -gA NAME=()` to reassert the type.
- Do not build a `mapfile -t ARR < <(pipeline)`-then-`wait -n`-dispatch worker pool without a
  bare `wait` between the mapfile and the dispatch loop — see Key Decision 3.
- Do not verify "worker cap N was never exceeded" with a bare, non-atomic counter file under
  real concurrency — see Key Decision 4. Use `flock`-guarded increments, or real timestamp-
  overlap checking.
- Do not re-attempt the Phase 4-deferred "per-gate `CURRENT_GATE` scoping" item as a literal
  variable-restructuring task — it is already resolved structurally by the existing per-gate
  subshell (Phase 6's `gate_registry_exec_bounded`), which every gate (concurrent or not) already
  runs inside.

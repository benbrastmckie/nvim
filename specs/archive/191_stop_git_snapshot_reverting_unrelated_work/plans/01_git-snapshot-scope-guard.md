## Overview

`git-snapshot.sh` in its default (and `--branch`) mode reverts the WHOLE dirty working tree,
including tracked modifications that have nothing to do with the task being snapshotted. The fix
is a runtime scope guard inside the script itself: before reverting anything, classify every
dirty tracked path against the task's declared `file_scope` in `specs/state.json`, and refuse
(naming every offending path) rather than sweeping unrelated work away, unless an explicit
`--allow-out-of-scope` override is passed. A fixture test built on the repository's existing
shell-test convention proves the refusal, and four documentation/contract edits stop plan authors
from re-inventing the unsafe bare-default idiom. Done when: the fixture test passes against the
fixed script (and demonstrably failed against the unfixed one), `--no-revert` is byte-identical
in behavior, and no generated-plan guidance still endorses a bare precautionary
`git-snapshot.sh {N}`.

**SOURCE STORE IS THE EDIT TARGET**: every edit below lands in `agent-system/extensions/core/`.
`.claude/**` is a disposable deploy artifact regenerated by Phase 6 and is NEVER hand-edited
(see `.claude/rules/source-store-deploy-boundary.md`).

## Decisions

- **D1 — Where the matching logic lives**: a new, additive `path_covered_by_scope()` bash
  function in `agent-system/extensions/core/scripts/lib/file-scope-overlap.sh`, with a
  "Containment vs. overlap" subsection added to its governing document
  `context/patterns/file-footprint-overlap.md`. Rationale: that document declares itself the
  single source of truth and forbids consumers restating the rule locally; a private copy inside
  `git-snapshot.sh` would be the fourth transcription. The new function answers a *different,
  one-directional* question (is one concrete path covered by a declared scope?) from the
  existing symmetric scope-vs-scope `scopes_overlap()`, so it is a sibling, not a replacement.
- **D2 — Guard applies to BOTH reverting modes** (`default` and `--branch`), not the literal
  word "default" only. `--no-revert` is never guarded (it reverts nothing, so it has nothing to
  destroy).
- **D3 — Tracked-only refusal**: only dirty *tracked* paths outside scope trigger refusal, per
  the dispatch's acceptance criterion. Out-of-scope *untracked* paths that `-u` would delete are
  enumerated as a loud stderr WARNING in reverting modes but do not refuse.
- **D4 — No-`file_scope` fallback is fail-closed**: when the resolved task has an absent or
  empty `file_scope`, or `jq`/`specs/state.json` is unavailable, a reverting mode REFUSES with a
  message naming the reason and the `--allow-out-of-scope` override. Rationale: an undeclared
  scope means the script cannot distinguish task work from unrelated work — precisely the state
  that produced the incident. Silent-revert-by-default is the defect; a loud, overridable stop
  is the fix.
- **D5 — Override flag name is `--allow-out-of-scope`**, deliberately NOT reusing or extending
  the three-way mutually-exclusive mode selector. It is an independent boolean and must not be
  confusable with `--no-revert`, which solves the different problem of durable-without-reverting.

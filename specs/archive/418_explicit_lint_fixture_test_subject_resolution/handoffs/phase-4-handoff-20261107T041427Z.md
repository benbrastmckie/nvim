**Key Decisions Made**:
- **Phase 3 regression found and fixed** (commit b30cc0808, before Phase 4 work began): the two
  confirmed non-default-order callers migrated in Phase 3
  (`test-gate-out-derived-staleness.sh`, `test-install-uninstall-extension.sh`) passed
  `common_test_resolve_subject`'s positional candidate arguments in the OLD
  `resolve_candidate` first-tried/second-tried order (source-store in slot 3, deployed in
  slot 4) instead of the function's fixed `<deployed_candidate> <source_store_candidate>`
  contract. Since `mode=source-store` reads only slot 4, both suites were silently declaring
  and resolving the DEPLOYED copy -- confirmed empirically via their own `[SUBJECT]` output --
  despite the mode name and the plan's own verification note claiming otherwise. Fixed by
  swapping the two candidate arguments at all 8 call sites across the two files. **Any future
  phase that migrates a "source-store-first" or "hard-selected deployed" caller MUST pass the
  deployed candidate in the 3rd positional slot and the source-store candidate in the 4th,
  regardless of which one was historically tried first** -- the function's mode selects which
  SLOT it reads, not which ARGUMENT POSITION was first in the old helper's call.
- `test-force-phases.sh`'s local `resolve_inverted` diverged from a verbatim
  `common_test_resolve_candidate` copy: it was source-store-first WITH a deploy fallback
  ("the documented absent-fallback"). Preserved via `mode=source-store` (strict, no fallback)
  rather than inventing a new mode, since the suite's own harness-sanity check already treats
  any non-source-store resolution as exit 2 -- the fallback was already unreachable in
  practice and the observable behavior is unchanged.
- Gate 27's `MISSING_DECLARATION` check is a naive whole-file `grep -c` substring count of
  `common_test_resolve_subject` vs `common_test_declare_subject` occurrences (not call-site
  paired). An explanatory comment naming the resolver function by its literal identifier
  (without an equal-count mention of the declare function) trips a false-positive violation.
  Hit 3 times during this phase (test-force-phases.sh, test-lint-json-channel-discipline.sh,
  test-orchestrate-build-dispatch.sh); fixed by rephrasing comments to say "the shared
  resolve-subject helper" instead of the literal identifier. **Future phases (5, 6): avoid
  writing the literal string `common_test_resolve_subject` in prose comments unless
  `common_test_declare_subject` appears an equal number of times in the same file** -- run
  `grep -c` on both names per file before considering a migration complete.
- The two `*_CANDIDATES=()` array loops found incidental to Group B migration (one in
  `test-lint-postflight-boundary.sh` resolving a fixture TARGET SKILL.md, not the lint
  subject-under-test) were also migrated to the explicit helper rather than left as
  permanent exemptions, since they resolve the same deployed/source-store duality and the
  gate-27 lint's inline-array check would otherwise still flag them.

## Findings

### Codebase Patterns

**Current defect, confirmed at the code level** (`claude-refresh.sh:566-571`,
`claude-refresh.sh:709`, `claude-refresh.sh:486-487`):
```bash
get_vmswap_kb() {
    local pid="$1"
    local kb
    kb=$(awk '/^VmSwap:/ {print $2; exit}' "$PROC_ROOT/$pid/status" 2>/dev/null || true)
    echo "${kb:-0}"
}
```
`run_claude_pass()` computes `combined=$((rss + swap_kb))` per-PID and sums across all matched
rows; `detect_lean_candidate_trees()` does the same (`mem_total=$((mem_total + row_rss[m] +
swap_kb))`) per tree member. Neither distinguishes private (anonymous) memory from file-backed
shared pages (mmapped `.olean` files), so N workers sharing a 5.6 GB library each contribute the
full RSS of those shared pages to the tree total -- this is exactly the "15.1 GB reported, ~2.3
GB real" defect named in the dispatch.

**`PROC_ROOT` seam already exists and is the correct extension point**
(`claude-refresh.sh:551-555`):
```bash
PROC_ROOT="${PROC_ROOT:-/proc}"
```
Currently only `get_vmswap_kb()` reads through it. The new `smaps_rollup`-reading helper should
read `"$PROC_ROOT/$pid/smaps_rollup"` through the SAME seam, so existing and new tests share one
fixture-root convention. No second seam should be introduced.

**`smaps_rollup` format** (not read anywhere in this repo today -- net new). Its fields of
interest, each a `Field:    NNNN kB` line exactly like `/proc/PID/status`'s `VmSwap:` line the
existing `awk` idiom already parses:
- `Pss_Anon:` -- anonymous (non-file-backed) proportional set size: this is the task's
  "reclaimable" numerator alongside swap.
- `SwapPss:` -- this PID's *proportional* share of swapped-out pages (NOT the same field as
  `/proc/PID/status`'s `VmSwap`, which is this PID's full swap usage with no de-duplication
  across sharers -- using `VmSwap` here would reproduce a milder version of the same
  double-counting defect for swapped shared pages). The dispatch's formula
  `reclaimable = Pss_Anon + SwapPss` is consistent with using the PSS (proportional) family
  throughout, not mixing it with the non-proportional `VmSwap`.
- `Pss_File:` -- file-backed (mmapped) proportional set size: report separately as "shared cache
  (not counted)," per the dispatch. This is the quantity that was being misreported as
  reclaimable before.
- A kernel without `/proc/PID/smaps_rollup` (older kernels; some containers) will have the file
  absent or unreadable -- this is the fallback trigger the dispatch names explicitly ("label the
  figure approximate"), distinct from a PID that has already exited (which the existing
  `get_vmswap_kb()` already treats as benign-zero, not fallback).

**Existing fixture idiom to extend, not replace** (`test-claude-refresh-matcher.sh:318-346`,
assertion (e)): fixtures are plain files under `$WORKDIR/fakeproc/<pid>/status` written via
`printf`/heredoc, read through `PROC_ROOT="$FAKE_PROC_DIR"`, with `PROC_ROOT` unset immediately
after each isolated-helper case to prevent leakage into later assertions. The output-shape case
(same assertion block, lines 362-413) additionally drives a fake `ps` placed first on `$PATH`
(detecting the invoked field-spec via a `case "$field_spec" in *pgid*) exit 0 ;; esac` guard to
stay inert for passes it isn't built for) plus a fixture `/proc/<pid>/status`, then asserts on
the full `--dry-run` text output rather than only the isolated function's return value -- this
is the idiom that catches "field-count mismatch between the write site and the read site," and
the dispatch's (d) acceptance bar (fixture of N workers sharing a large `Pss_File`) should follow
this same two-layer pattern: (1) a direct call to the new helper with a multi-field
`smaps_rollup` fixture, and (2) a full-script `--dry-run` run with a fake `ps -C lake,lean`
(reusing assertion (g)'s exact fake-`ps` technique at lines 567-620) showing the de-duplicated
total in the rendered table.

**`lean_row_is_idle()`'s pcpu comment is already partially correct and needs a narrow fix, not a
rewrite** (`claude-refresh.sh:330-338`): the existing comment already calls `pcpu` "a decaying-
average percentage" -- this is the inaccuracy the dispatch's (c) targets. procps-ng's `pcpu` is
documented as "cpu utilization of the process in \"##.#\" format... currently is cputime/realtime
percentage," i.e. lifetime-average, not an exponentially-decaying recent average (that
characterization applies to `top`'s live-refresh `%CPU`, not `ps`'s static `pcpu` column). The
fix is a comment/prose correction only, per the dispatch's explicit note that "the idle gate
itself is replaced by a follow-on task" -- do NOT touch the `lean_row_is_idle()` logic itself in
this task; the CPU-delta state machine (absorbed-218, work item (a)) is the actual gate
replacement, and it is explicitly a SEPARATE function/mechanism added alongside (ultimately
superseding in effect, but the dispatch does not ask to delete `lean_row_is_idle()` or its
`pcpu`/`etimes` fields from the snapshot -- only to stop relying on `pcpu` as an idleness signal
once the CPU-delta gate exists). The planner should decide explicitly whether `lean_row_is_idle()`
is retired or left dead-but-present; the dispatch text ("Replace the pcpu/etimes gate entirely")
in absorbed-218 implies retirement of its idleness *decision*, but the predicate function itself
may still be useful for the `(f)` test suite's existing cross-contamination assertions unless
those are also rewritten. Flag this as a planning decision, not a research-resolvable ambiguity.

**No code in this repo parses `/proc/PID/stat` today.** The CPU-delta tracker (absorbed-218 (a))
needs `starttime` (whitespace-field 22) and the dispatch also implies reading `utime`+`stime`
(fields 14+15) for the "summed utime+stime of all tree members" cumulative-CPU-ticks figure.
**Known gotcha, not yet encountered elsewhere in this codebase**: `/proc/PID/stat`'s second
field, `(comm)`, is parenthesized and MAY itself contain spaces or embedded parentheses (process
names can be renamed via `prctl(PR_SET_NAME)` to include spaces). The only safe parse is to find
the LAST `)` in the line (not the first), then split the remainder by whitespace, counting
fields 3 onward from there -- the standard, well-documented `/proc/pid/stat` parsing gotcha
(`man proc`'s own worked example for this file explicitly warns about it). This is worth a
researched, named risk below because a naive `awk '{print $22}'`-style split (which the
`VmSwap`/`smaps_rollup` helpers' flat-line parsing style might tempt a reuse of) will silently
misparse any tree member whose `comm` contains a space.

**Atomic state-file write precedent already exists** (`scripts/state-write.sh:445-475`): private
`mktemp` file in the SAME directory as the final target, written, then `mv "$STAGE_FILE"
"$STATE_FILE"` for an atomic rename. `state-write.sh`'s full machinery (locking, spill files,
jq validation) is far heavier than the new `lean-trees.json` tracker needs, but the core
`mktemp`-in-same-dir + `mv` idiom is the directly reusable piece; absorbed-218's own (b)
("State file writes atomic (tmp + mv)") names exactly this idiom. `~/.local/state/claude-refresh/`
does not yet exist as a directory in this repo (it's a runtime path, not a repo path) -- the
script will need an idempotent `mkdir -p` at the point of first write, with a corrupt/missing-
file-tolerant read path per absorbed-218 (b)'s explicit "treat as first sighting, NEVER as idle"
instruction.

**`systemd-run` availability-probe + audible-degrade pattern already exists and is directly
reusable** (`scripts/lake-build-guard.sh:617-623`):
```bash
command -v systemd-run >/dev/null 2>&1 || return 1
systemd-run --user --scope --quiet --collect -- true >/dev/null 2>&1
```
with the file's own header naming the governing principle: "degrade audibly, never silently: a
missing optional dependency (flock, systemd-run, PSI) ...". The notify-before-kill pass
(absorbed-219 (d): "Degrade gracefully when notify-send, systemd-run, or a DBus session bus is
absent: log only, never kill") should follow this exact two-step probe shape for `systemd-run`,
add an equivalent `command -v notify-send` check, and add a DBus-session-bus check (e.g. test
`$DBUS_SESSION_BUS_ADDRESS` is non-empty, or probe `dbus-send --session ... org.freedesktop.DBus.ListNames`
cheaply) -- no DBus-check precedent exists elsewhere in this repo, so this is net-new but low-risk
plumbing.

**`notify-send`/`systemd-run` are NOT currently invoked from `claude-refresh.sh` or
`skill-refresh`/`refresh.md` at all** -- confirmed via repo-wide grep. The Lean extension's
`lean-comparator-run.sh`/`lean-sorry-census.sh` use `notify-send`/`systemd-run` for unrelated
long-running-job notifications; worth a quick comparison read if the planner wants a second
reference pattern, but they are a different extension (`agent-system/extensions/lean/`, not
`core/`) and not in this task's `file_scope`.

**`main()`'s argument parsing is a flat zero-value `case`** (`claude-refresh.sh:1709-1747`):
every existing flag (`--force`, `--dry-run`, `--help`) is a boolean toggle; none take a value.
Absorbed-219 (b)'s planned `--lean-tree <pid>:<starttime> --force` invocation mode needs:
(1) a new case arm that captures a value (`--lean-tree=*` or a following-arg convention --
neither precedent exists in this file; pick one and document it in `print_help()`), (2) a new
code path that does NOT run all five passes unconditionally (unlike every existing invocation
shape) but instead re-verifies starttime identity + still-idle + still-over-floor for exactly one
named tree before running the EXISTING ordered-termination sequence
(workers -> server -> root, already implemented inside `run_lean_pass()`'s `--force` branch at
lines 892-916) -- this re-verification logic does not exist yet and is new. The cleanest
structural fit is a new `run_lean_tree_targeted_termination()` function that reuses
`detect_lean_candidate_trees()`'s tree-assembly logic (filtered to the one matching root pid +
starttime) rather than duplicating the ordering loop.

## Decisions

- **One shared helper, not two.** The dispatch is explicit: "Add one shared memory helper used
  by BOTH passes." Both `run_claude_pass()` and `run_lean_pass()`/`detect_lean_candidate_trees()`
  should call the same new function (proposed name: `get_pss_reclaimable_kb()`, returning
  `reclaimable_kb|shared_cache_kb|is_approximate` as a pipe-delimited single line, mirroring this
  file's existing `member_details` pipe-delimited convention) rather than each pass growing its
  own parsing logic.
- **Read `smaps_rollup` only for already-narrowed candidates**, per the dispatch's "Read only for
  candidates (not every process)" -- this is already the existing design shape (`get_vmswap_kb`
  is likewise only called after `is_claude_executable_comm`/Lean-comm gating), so no new
  candidacy-gating logic is needed, only a call-site swap.
- **Keep `VmSwap`/`get_vmswap_kb()` as the explicit fallback path**, not a parallel/competing
  implementation -- the dispatch's fallback instruction ("fall back to RSS + VmSwap... label the
  figure approximate") means the new helper should internally degrade to the existing
  `get_vmswap_kb()` + the snapshot's own `rss` field when `smaps_rollup` is unreadable or
  incomplete, not introduce a second independent swap-reading code path.
- **`lean_row_is_idle()`'s pcpu comment fix is textual only in this task**; the CPU-delta
  idleness decision is a new, separate mechanism. Leave this as an explicit open question for the
  plan to resolve: does `lean_row_is_idle()` get deleted once the CPU-delta gate lands, or kept
  dormant? (See Findings above.)
- **New state file path and read/write seam should mirror `PROC_ROOT`'s override-for-testing
  shape**: e.g. `LEAN_TREE_STATE_DIR="${LEAN_TREE_STATE_DIR:-$HOME/.local/state/claude-refresh}"`,
  so tests can point it at a fixture directory exactly as they already do for `PROC_ROOT`.
- **The `--lean-tree` mode is a structural, not additive, change to `main()`** and should be
  called out to the planner as its own phase with its own acceptance criteria (starttime
  re-verification refusal, still-idle re-check refusal), not folded silently into the existing
  five-pass sequence.

## Risks & Mitigations

- **Risk: `SwapPss` absent on an older kernel's `smaps_rollup`.** Mitigation: the fallback
  trigger must check for presence of ALL required fields, not just file-readability, and label
  approximate in that case too (see External Resources note above).
- **Risk: `/proc/PID/stat` comm-field parsing gotcha silently miscounts CPU ticks for a tree
  member with a space in its reported name.** Mitigation: implement the `)`-anchored parse from
  the start (see Findings); add a fixture row with a deliberately space-containing fake `comm` to
  the CPU-delta test suite to prove the parser is robust, not merely untested against the common
  case.
- **Risk: scope creep / 2-hour estimate mismatch.** Three absorbed tasks, each with their own
  multi-part acceptance bar and test matrix, bundled into one `effort: 2 hours` estimate inherited
  from the original (unmerged) task 217 alone. The planner should either re-estimate honestly
  across all three phases or explicitly scope Phase 1 as the deliverable for this round and
  phases 2-3 as follow-on rounds within the same task number -- flagging this rather than
  silently under-delivering against the full dispatch.
- **Risk: `main()`'s structural change for `--lean-tree` interacts with the always-run-five-passes
  invariant the systemd unit's own header comment (`claude-refresh.service`) explicitly documents
  and relies on ("New-passes ruling... confirmed at code level... main() calls exactly five pass
  functions... all unconditionally").** The `--lean-tree` mode must be an explicit early-return
  branch in `main()` BEFORE the five-pass sequence, never a sixth pass folded into it -- otherwise
  the hourly unit's `ConditionPathExists`/`--dry-run` safety reasoning documented in that file's
  own header comment would need re-deriving. This is a MUST NOT violation risk if implemented
  carelessly, not just a style concern.
- **Risk: notify-send/mako action-string behavior is asserted from the dispatch's own live
  observation (DESIGN REFINEMENT), not independently re-verified here** (no live mako environment
  available during research) -- implementation should treat the `-A default=Kill` / dismiss-as-
  keep behavior as given (it is a first-hand, dated observation already in the dispatch, not
  something research can add confidence to) but the manual end-to-end acceptance check named in
  the dispatch's own ACCEPTANCE line remains the real verification gate, not the unit tests alone.

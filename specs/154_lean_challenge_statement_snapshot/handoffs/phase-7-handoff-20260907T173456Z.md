## Key Decisions Made
- Script invocation convention: `lean-challenge-snapshot.sh` MUST be invoked with CWD set to the
  target project's own repo root (or a directory containing its specs/ tree) -- specs/ is
  resolved relative to CWD, and R2's "plan's approval commit" is resolved via
  `git -C PROJECT_ROOT log -- <plan-path-relative-to-project-root>`. This assumes (and requires)
  the plan and the target .lean sources share ONE git repository -- the normal case for a
  lean/lean4 task, whose own specs/{padded}_{slug}/ tree lives inside the project it concerns.
- `git commit --allow-empty` is used when writing the Challenge, so a byte-identical
  regeneration (e.g. --force re-run against an unchanged plan) still produces a genuinely new
  commit SHA rather than failing with "nothing to commit".
- Status gate treats {not_started, researching, researched, planning, planned} as pre-implementation
  (allowed without --force); everything else (implementing, pr_ready, completed, blocked, partial,
  abandoned, expanded) is refused with exit 73.
- `--check`'s current-tree search EXCLUDES the manifest's own challenge_path file, to avoid a
  trivial self-match against the pinned Challenge artifact itself sitting in the tree.
- content_sha256 is computed independently of git, over the assembled module bytes, as a second
  immutability witness.

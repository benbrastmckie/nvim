**What now exists**: `verify-deploy.sh --skip-unchanged` consults a per-gate, content-addressed
cache (`specs/.gate-cache/gateN.json`, gitignored, outside `.claude/` so it survives
`deploy-headless.sh`) before dispatch. A cache HIT removes that gate id from the dispatch set
entirely (via the new `gate_registry_exclude_ids`), emits `[SKIP-CACHED] gateN (<name>) --
inputs unchanged since <timestamp> (<digest>)`, and increments `SKIPPED_CACHED`. A gate that
actually ran and finished with zero findings/failures writes a fresh green entry; a gate that
failed, warned, timed out, or self-skipped invalidates any existing entry instead. The default
(flag-absent) path is proven byte-identical to pre-change behavior at the `--findings` interface,
including both the PASS and FAIL summary-line branches.

**The unplanned performance fix, this phase's single most consequential finding**: Phase 3's
`gate_cache_corpus_digest` hashed a gate's resolved corpus via one `git hash-object` subprocess
PER FILE. Three real gates declare a ~4815-file corpus (`@extensions,.claude`); Phase 3's own
synthetic-fixture test suite never exercised anything near this scale. Measured cold: the full
23-gate consult loop took 75.6s even on a lightly-loaded host, and one gate alone could take
18-51s under contention — which would have defeated the whole feature (paying ~75s to learn you
can skip gates is not a win). Fixed via (1) batched hashing (`git hash-object --stdin-paths`,
one call per corpus instead of one per file), (2) replacing two O(n)-with-bad-constant bash
string-concatenation loops with vectorized array-expansion/`paste` joins, and (3) per-process
memoization keyed by (corpus spec, root) for the corpus digest and by root alone for the
implementation digest's `scripts/lib/` component (11 gates share the bare `@extensions` spec, 3
share `@extensions,.claude`, and most gates reference at least one bash script). Final measured
result: the full 23-gate consult loop now runs in 4.4s. All 16 pre-existing Phase 3 test cases
still pass unchanged (none assert a literal digest string).

## Key Decisions Made

- **Store location**: `specs/.gate-cache/`, not under `.claude/**` (wiped by every
  `deploy-headless.sh` run, which precedes every `verify-deploy.sh` run that matters) and not a
  bare repo-root directory (an unnecessary second gitignore-policy surface alongside the
  established `specs/`-scoped ephemeral/machine-local-state convention `.orchestrator-deploy-ledger.json`
  already uses for the identical kind of thing). Confirmed outside gate 13's scan scope by
  reading `manager.find_orphans`'s Lua source directly (`target_dir = project_dir .. "/" ..
  config.base_dir`, i.e. `.claude/` only).
- **Cacheability determined via two new indexed arrays (`GATE_RAN_LIST`, `GATE_DIRTY_LIST`),
  never via global CHECKS/FAILURES deltas**: the existing concurrent-batch reconciliation
  mechanism (`gate_registry_exec_concurrent_batch`'s snapshot-then-delta-apply protocol) only
  correctly reconciles indexed arrays and scalars, not associative arrays, and a per-gate
  CHECKS/FAILURES delta is not recoverable from the shared, cumulative globals alone once
  multiple gates have run concurrently in the same wave. `GATE_DIRTY_LIST` is appended to
  unconditionally by `warn()` (not gated by `--findings`), since it is pure internal bookkeeping,
  never part of the public findings interface.
- **The consult loop must filter through `gate_selected()`**: see the bug fixed above. A
  cache-hit gate outside the current `--only-gate`/`--max-cost` selection must be invisible to
  the consult loop entirely, not merely excluded from dispatch after being announced.
- **`gate_registry_exclude_ids` added to `gate-registry-lib.sh`** (outside this phase's originally
  declared file list, but necessary): the existing dispatch mechanisms
  (`gate_registry_exec_concurrent_batch`, the sequential loop) both read `_GREG_IDS` directly with
  no gate-id-list parameter of their own, so making a cache hit actually SKIP a gate's real cost
  (not merely silence its narrative output, which is all `--only-gate`'s pre-existing
  `gate_selected()` mechanism does) required a primitive that narrows the loaded id set itself.

## What NOT to Try

- Do not revert to a per-file `git hash-object` loop, or to a per-element bash string-
  concatenation loop for building a path list or a path+hash fold, for ANY corpus-scale
  operation in this library — both were measured and are the two root causes this phase's
  performance fix closes. Any future addition to `gate-cache-lib.sh` that walks a
  potentially-large file set should batch via `git hash-object --stdin-paths` and join via
  `paste`/array expansion, not a loop.
- Do not pass a made-up or unverified objective id to `git-commit-phase.sh --objective` — it
  correctly narrows derivation to exactly that id's own `files_touched`, and a nonexistent id
  derives an EMPTY set with only a non-fatal warning, which is easy to misread as benign. Verify
  `git status`/`git diff --stat` immediately after any `--objective`-scoped commit, and use the
  bare (no `--objective`) phase-closing form, which unions every objective in the progress file.
- Do not assume the pre-dispatch consult loop composes correctly with `--only-gate`/`--max-cost`
  just because it reads the "currently loaded" `_GREG_IDS` — `_GREG_IDS` is never narrowed by
  those flags (only each gate's own internal `gate_selected()` guard is), so the consult loop
  needs its OWN explicit `gate_selected()` check.

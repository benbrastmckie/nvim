## Key Decisions Made

- **Behavior-switching fake scripts, not real-cache-state comparison, for the two
  `deploy_findings_snapshot` unit cases.** A gate's own clean findings output is identical
  whether it ran for real and passed or was cache-skipped and the cache happened to be correct --
  the black-box FINDING-line interface cannot distinguish these when the live gate state is
  currently clean. A fake script that only emits a FINDING on the "full-run" branch makes the
  internal state directly observable instead.
- **Symlinked `agent-system/` into the scratch target for the three interface-level fail-open
  cases**, rather than hand-building a complete fake source tree: `gate_cache_implementation_digest`
  resolves `verify-deploy.sh`/`gate-registry.data`/`scripts/lib` relative to the TARGET root
  itself, so a scratch target lacking these at the expected relative path makes every composite
  key compute to the `CANNOT_COMPUTE` sentinel and no cache entry is ever written -- there is
  nothing to corrupt. The symlink gives full resolvability for the implementation digest while
  the CORPUS (gate 1's nine `.claude/` files) stays entirely scratch-local and isolated from the
  live repo's own `specs/.gate-cache/`.
- **Gate 1 ("Event-store and error-store files") as the test gate** for the interface-level
  cases: cheap, `cost_class free`, and its corpus is nine literal paths trivial to stand up in a
  scratch `.claude/` tree.
- **A control case precedes the three negative cases**: confirming a genuinely matching warm
  entry DOES skip (before testing that a corrupted one does not) proves the test harness itself
  is wired correctly, so a false PASS on the three negative cases can't be mistaken for "the
  feature is safe" when it might actually be "the harness never exercised the skip path at all".

## What NOT to Try

- Do not attempt to prove `deploy_findings_snapshot`'s warm-cache-full-run property by comparing
  real findings output with the cache warm vs. cold against a currently-clean gate -- the two
  scenarios are observationally identical at that interface. Use a behavior-switching fake script
  instead.
- Do not build an interface-level gate-cache test target without symlinking (or otherwise
  providing) a resolvable `agent-system/extensions/core/scripts/verify-deploy.sh` (or
  `.claude/scripts/verify-deploy.sh`) under the scratch root -- `gate_cache_composite_key` will
  silently return the sentinel for every gate and no cache entry will ever be written, with no
  error raised to say why.
- When computing a path N levels above a `CORE_DIR`-style variable in a `scripts/tests/*.sh`
  suite, verify what `CORE_DIR` actually resolves to in THAT file first (it is
  `.../core/scripts` in `test-deploy-baseline-lib.sh`, not `.../core` -- confirmed via the
  pre-existing `site_mismatch` case's own path construction) rather than assuming it matches a
  value from a different file or phase.

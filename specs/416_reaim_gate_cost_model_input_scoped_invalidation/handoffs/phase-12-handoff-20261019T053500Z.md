  theoretical "CPU/core oversubscription" framing: this host has 24 cores (not the constraint),
  but Phase 10 measured gate 8's own internal pool peaking at 21,952MB/30GiB, and this phase's
  own live check found only ~5.3GB available with 7.4GB already swapped on this shared,
  multi-session host.
- The measured maximum upside is bounded and modest: gate 8 alone 663s (host NOT idle, 1-min
  load 2.50 at start -- directionally valid, not a Phase-1-harness-certified sample) against the
  rest of the pool (gates 1-7,9-23, excluding 8) at 107s (load 0.67-1.71, reasonably idle).
  Perfect overlap could save at most ~107s off a ~700-770s total -- roughly 14%.
- Achieving that 14% safely would require NEW shared-concurrency-budget coordination between two
  independently-scheduled worker pools that neither scheduler supports today; a naive static
  split risks giving most of it back to each pool's own now-slower wall clock.

## Key Decisions Made

- **Treated this as a sizing-and-risk analysis, not a live overlap experiment.** Given the
  bounded ~14% upside and the host's own live memory-margin tightness, actually attempting a
  concurrent overlap run (which would add MORE memory pressure on an already-tight host, shared
  with other concurrent sessions) was judged not worth the risk for the information it would
  yield -- the sizing math already answers the question with the same confidence a live
  experiment would, at much lower risk to the shared host.
- **Distinguished the TWO candidate blocking issues and resolved one, kept the other.** The
  cache-store contention audit (genuinely new, introduced by this task) is CLEAR. The
  ambient-resource-pressure concern (inherited from task 411, now sharpened to specifically
  MEMORY rather than CPU) is the one that remains unresolved and is the actual basis for keeping
  gate 8 serialized.

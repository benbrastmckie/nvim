## Overview

The gate set's largest available reduction is not running a full sweep faster -- it is not
running one. Extend the declarative gate registry so every gate declares the input corpus it
reads, content-address that corpus, and skip any gate whose inputs and implementation are
byte-identical to those of its last green run. The full sweep remains the default and remains
what a plan's final verification gate gets; the skip path is opt-in, loudly visible per gate, and
fails open to a full run on any cache doubt. Alongside that, root-cause the 4.4x discrepancy
between gate 8's measured 457s and the 103s its own scheduler projected, then work the inherited
efficiency phases against a post-invalidation measurement rather than against the pre-invalidation
one that justified them. The edit target is the source store
`agent-system/extensions/core/**` (resolved from `.claude-extensions.json`'s
`extensions.core.source_dir`); `deploy-headless.sh` runs afterwards.

### Research Integration

No research report exists for this round. The dispatch itself supplies the measured model
(`measure-gate-costs.sh`, idle, 1-minute load 1.03 at start, twice averaged): `gate8` 457,197ms,
`gate3` 125,669ms, `gate22` 54,716ms, with the remaining twenty gates together under 57s. Three
gates are 87% of a ~694s sweep; seventeen are under 2000ms each. Three dispatch-era premises are
recorded as disproved and are not re-adopted anywhere below: shellcheck at 542s/40% of the set
(measured 54.7s, third cost centre); the nested-invocation "straggler" lever (already largely
spent); and "six lints share one `git ls-files` enumeration" (only `lint-shellcheck.sh` uses
`git ls-files`).

Four load-bearing facts were established live during planning, against the source store, and are
what the invalidation design is shaped around:

1. **The registry row is positionally parsed with eight TAB-separated fields.**
   `gate_registry_load` (`lib/gate-registry-lib.sh:183`) reads them via
   `IFS=$'\t' read -r id name invoke deps rss timeout class ser`, and the file's own header
   documents why a genuinely empty field is unusable: bash treats tab as IFS-whitespace even as
   IFS's sole member, so consecutive delimiters collapse and shift every later column. A ninth
   `input_corpus` field must therefore carry an explicit `-` placeholder, exactly as
   `dependencies` already does, and the loader must normalize it the same way.

2. **The summary line is a consumer interface, not decoration.**
   `verify-deploy.sh` closes with `[verify-deploy] PASS -- $CHECKS check(s), 0 failure(s)`, and
   `CHECKS` is incremented only by `pass()`, `fail()` and `warn()`. A cache-skipped gate that
   silently does not increment `CHECKS` changes that line's number on every incremental run. The
   extra clause reporting skipped gates must therefore be emitted only when the skip count is
   non-zero -- which is unreachable without the opt-in flag -- so the default path stays
   byte-identical.

3. **A skip that lands on one side of a findings baseline and not the other is a correctness
   hole, not a speedup.** `deploy_findings_snapshot` (`lib/deploy-baseline-lib.sh:146`) is called
   in pre/post pairs by `orchestrate-cycle-plan.sh` (`:969`, `:1037`, `:1113`),
   `command-gate-out.sh` (`:235`, `:258`) and `orchestrate-batch-gate.sh` (`:112`, `:124`) -- one
   of which gates whether an orchestration batch proceeds. If the post run skips a gate the pre
   run executed, a finding introduced by the very change under test disappears from the diff. The
   fast path must be structurally unreachable from these callers.

4. **A deployed-tree cache would be wiped by the thing it accelerates.** `.claude/**` is a
   disposable deploy artifact regenerated by `deploy-headless.sh`, and `deploy-headless.sh` is
   what runs immediately before `verify-deploy.sh`. A cache stored inside the deploy tree is
   therefore empty on exactly the runs that matter. The store must live outside the deploy tree,
   must be untracked, and -- because gate 13 does whole-tree orphan detection and gate 14 checks
   runtime-file tracking policy -- must be proven not to trip any gate that enumerates the tree.

### Decisions

**Order: invalidation first, then the inherited efficiency phases.** The dispatch asks for this
order to be decided deliberately rather than inherited. Invalidation is sequenced first because
it is the only lever that removes a gate from a run entirely, and because it changes the
measurement that justifies phases 8, 10, 11 and 12 -- working those first would size them against
a sweep shape that invalidation then dissolves. Each inherited phase is therefore re-evaluated
against a post-invalidation measurement before it is executed, and a phase whose premise that
measurement does not support closes as `[COMPLETED WITH EXCLUSIONS]` with the measurement as
Evidence. That is a recorded outcome, not a scope loss.

**Exception: the harness hardening lands first regardless.** Phase 1 is the inherited harness
work, placed in wave 1 with no dependencies, because without it no before/after this task takes
can be trusted. The precedent is concrete: a run begun at load 1.46 was contaminated mid-flight by
an unrelated sibling build and reported gate1 10ms -> 1,235ms and gate3 125.7s -> 299.0s with its
two runs disagreeing 404s against 193s, and the CSV it wrote was mechanically indistinguishable
from a clean sample.

**Only a green gate is cached.** A failing gate is never recorded as a cache entry and is never
skipped, so a replayed failure cannot exist and a real failure cannot be cached away. The
alternative -- caching a finding set and replaying it -- was rejected: it makes the findings
interface a function of cache state, which is exactly the property fact 3 above says must not
hold.

**The gate's own implementation is part of its cache key.** Keying on the input corpus alone
would skip a gate whose lint script was just rewritten. The key covers the corpus digest, the
gate's invoke function body, the script it invokes, the shared libraries it sources, its own
registry row, and the target mode -- see Phase 3.

## Goals & Non-Goals

**Goals**:
- Every registry row declares the input corpus it reads, alongside the `timeout_s` and
  `cost_class` it already declares.
- Content-addressed invalidation: a checkout, a branch switch, or a `touch` causes no spurious
  re-run, and a real content change is never missed.
- Per-gate skip visibility: a reader can tell "skipped, inputs unchanged" from "passed" from
  "skipped, source-store-only" at a glance, with the reason and the digest on the line.
- Full-sweep correctness stays available and stays the default; the fast path is opt-in and is
  structurally unreachable from the findings-baseline callers, so a closure criterion cannot
  silently get it.
- Fail-open on cache trouble, fail-closed on assertions: a stale, absent, unreadable or
  ambiguous cache degrades to a full run, never to a false pass.
- Gate 8's 457s-versus-103s discrepancy root-caused to one of its three candidate causes before
  any further scheduling work is layered on it.
- The two verify-deploy-testing suites stop re-paying gate 3 and gate 22 against their own
  fixtures; the recursive gate tree is treated as a structural target.
- `JOBS_CAP` set from the post-invalidation pool rather than from a figure 2.9x too small.
- A measurement harness that marks its own samples invalid when contention touches them.
- Gate 3 and gate 8's serialized isolation each decided on a post-invalidation measurement.

**Non-Goals**:
- Weakening any gate's assertion, or any suite's assertion, to gain speed, in any amount.
- Caching or replaying a failing gate's finding set.
- Enabling the fast path by default, or inside `deploy_findings_snapshot`, or inside any
  plan's final verification gate.
- Gate 16's lean `routing_hard`/`routing_agents_hard` declarations and gate 20's eager-load
  budget overage. Both are known pre-existing, declared out of scope by the dispatch, and must
  not be attributed to this work.
- The three known pre-existing suite failures baselined by the framework task.
- Net deletion of the script or test corpus. That is the corpus-consolidation task's acceptance
  criterion, not this one's.
- Re-adopting any of the three disproved dispatch-era premises listed under Research Integration.

### Phase 3: Content-Addressed Corpus and Implementation Digest Library [COMPLETED]

a single content-addressed digest, with no mtime dependence anywhere in the computation.

stat-ing and requires content hashing. `git ls-files` and `git hash-object` give tracked content
addresses for free from the index, but untracked files inside a declared corpus (a newly added
script not yet staged) are invisible to them and must be hashed directly. The key must also cover
the gate's own implementation: the invoke function body lives in `verify-deploy.sh`, the work
lives in a separate script, and both source shared libraries.

      than re-walking. *(completed)*
- [x] Compute the corpus digest content-addressably: for tracked, unmodified paths use the blob
      id git already holds; for modified or untracked paths hash the working-tree content
      directly. Fold the sorted `path<NUL>blob` pairs into one digest so an addition, a deletion
      or a rename changes it. Prove the no-mtime property by asserting a `touch` of every corpus

## Rollback/Contingency

- Each phase is committed separately, so reverting one phase is a single-commit revert. Phase 2 is
  declarative-only and inert until Phase 5, so an interruption anywhere in waves 1-2 leaves a fully
  functional gate set.
- The skip path is opt-in at every layer. Disabling it is removing one flag from one call site, not
  reverting a migration -- so a correctness doubt discovered after the fact is resolved by not
  passing the flag, immediately, with no code change.
- Phase 4 is a decision gate in the sense `plan-format.md`'s "Decision gates and contingency
  branches" section defines: its verdict assigns the remaining scheduling work. If it finds the
  parallel path not delivering its resolved worker count, Phase 10's cap change is deferred behind
  that fix rather than layered on top of it.
- Phases 11 and 12 are derived additions and each is independently droppable: phases 1-10 stand
  without either, and dropping one does not change the other's premise. Each carries its own
  evidence gate, so a phase whose premise the post-invalidation measurement does not support closes
  as `[COMPLETED WITH EXCLUSIONS]` with that measurement as Evidence rather than being forced
  through. That is the expected outcome for at least one of them.
- Phase 8's narrowing is per invocation, so a case whose narrowed selection turns out not to cover
  what it asserts is reverted to its full-battery call individually, without disturbing the other
  cases in the same suite.
- Phase 10's cap change is a single constant: if the measured peak memory or concurrent-fixture
  count at the candidate cap is unacceptable, the cap stays at 4 and the header records why on the
  current evidence. That is a complete outcome for the phase, not a failure of it.
- The cache store is disposable by construction. Deleting it costs one full sweep and nothing else,
  which is also the recovery procedure for any suspected cache inconsistency.
- If a rollback must discard uncommitted work, take a snapshot first per
  `context/contracts/recovery.md`'s rollback rung (which names the exact invocation shape and its
  out-of-scope override flag) before running any destructive git command.
- `deploy-headless.sh` is re-runnable, so a bad deployed tree is repaired by redeploying from the
  reverted source store rather than by hand-editing `.claude/**`.
- On the concurrent-edit overlap with the corpus-consolidation task: if that task has started work
  on `tests/run-all.sh`, `suite-cost-hints.txt`, or either verify-deploy-testing suite when wave 3
  begins, add the dependency edge and wait rather than merging by hand. The overlap is in files
  whose correctness both tasks assert differently.

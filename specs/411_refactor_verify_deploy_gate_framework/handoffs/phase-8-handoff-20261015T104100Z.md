### Measured before/after (shellcheck specifically — this phase's whole purpose)

Three independent timing pairs were taken (varying ambient host load from concurrent sibling
agent sessions on this shared box — each pair is still a fair same-host A/B, since both legs of
a pair were measured back-to-back):

| Context | SHELLCHECK_JOBS=1 (forced single-worker) | Default (SHELLCHECK_JOBS=8) | Ratio |
|---|---|---|---|
| Manual direct invocation | 76,778 ms | 39,455 ms | 0.51x |
| Acceptance-suite run (Case 1, via `run-all.sh --only`) | 136,376 ms | 45,475 ms | 0.33x |
| Raw `xargs -P` exploration (not the shipped shape; used only to pick the worker cap) | P=1: 75,778 ms | P=8: 42,006 ms; P=12: 38,355 ms | 0.56x / 0.51x |

All three show a real win in the 1.8x-3x range (better than the research's budgeted 1.3-1.8x),

sides** (the real corpus is currently clean) — finding-SET equivalence, not just a timing
comparison, is the actual proof. Finding-set equivalence was additionally proven against the

## What NOT to Try

- Do not reintroduce a batched shellcheck-invocation shape (multiple files per `shellcheck`
  call, N such calls run concurrently) "to optimize further" — every batched shape measured by
  the research (`-P24 -n20`, `-P4 -n96`, `-P8 -n48`) was SLOWER than doing nothing; only true
  one-process-per-file dispatch wins. This is recorded in the script's own header now too.
- Do not pick `SHELLCHECK_JOBS` from a bare `nproc` — the measured curve plateaus well before
  core count (diminishing returns from 8 to 12 workers), and more workers raises shared-host
  contention risk for comparatively little further win.
- Do not use an absolute-ms threshold for the acceptance suite's timing gate — a relative ratio
  (parallel <= 80% of forced-single-worker, both measured back-to-back) is what survives genuine
  ambient host contention; precedent: `test-run-all-parallel.sh`'s own prior fix for the
  identical flakiness class.
- Do not trust `test-lint-shellcheck.sh`'s own PASS as evidence about a source-store-only
  lint-shellcheck.sh change pre-redeploy — it resolves deploy-tree-first (see Deviations above).

## Critical Context

### On the coordinator's drift-inspection question (Phase 4-deferred `CURRENT_GATE` scoping)

Investigated directly by reading the code (not re-asserting the Phase 7 handoff's own prose).
**Finding: genuinely discharged, not carried past its own phase.** Every gate's own
`gateN_run()` function sets `CURRENT_GATE="gateN"` as its first statement, inside its own
function body (verify-deploy.sh:505, :535, :589, ... — confirmed directly, this predates Phase
7 and was already true from Phase 4's migration). Since Phase 6, every gate (sequential or
concurrent) runs inside its own forked subshell via `gate_registry_exec_bounded` /
`gate_registry_exec_concurrent_batch`, and `CURRENT_GATE` is set INSIDE that subshell before any
`fail()`/`check()` call. Every `FINDINGS_LIST+=("FINDING $CURRENT_GATE ...")` string is therefore
baked with the CORRECT gate id at creation time, inside the correct subshell — confirmed there is
no other read site of `$CURRENT_GATE` anywhere in verify-deploy.sh outside those `fail()`/
`check()` helper calls (grep-confirmed: lines 445/447/461/463 only, all inside the synchronous
check-time helpers; the 124-timeout translation path at line ~1557 also sets
`CURRENT_GATE="gate${_gate_id}"` immediately before using it, same pattern). So concurrent gates
cannot cross-attribute a finding to the wrong gate id even though the bare global is still
reassigned repeatedly rather than being lexically scoped per-gate — the blast radius the Phase 4
deferral worried about cannot occur, structurally, regardless of worker count. This is a
legitimate closure, not an unverified assertion carried forward.

### Why this phase ran long

The worker-cap experiment and the acceptance suite's own real-corpus timing comparison both
require full ~387-file shellcheck scans (several per phase: sequential/parallel pairs, repeated
under load, plus the original-vs-new worktree comparison) — each full scan costs 40-140s
depending on ambient host contention from concurrent sibling sessions on this shared box. This
is expected per-phase cost for a phase whose entire point is a measured timing claim, not a
result of inefficiency in this dispatch.

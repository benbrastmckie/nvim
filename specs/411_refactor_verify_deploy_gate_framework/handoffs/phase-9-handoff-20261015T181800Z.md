## Key Decisions Made

- The master corpus is built via ONE `git ls-files -z -- agent-system/extensions` call inside a
  new `gate_registry_shared_corpus_build <root>` function in `gate-registry-lib.sh` (the
  producer), not inside `verify-deploy.sh` directly -- keeps the thin-interpreter library as the
  single home for every gate-infrastructure primitive, matching its own stated role.
- The consumer half (`common_shared_corpus_available` / `common_shared_corpus_files`) lives in
  `common.sh`, not `gate-registry-lib.sh`, because every affected lint already sources
  `common.sh` and none of them source the registry lib (they are standalone scripts invoked as
  child processes, not registry participants themselves).
- `common_shared_corpus_files` matches glob patterns against the FULL relative path (not just
  basename), using ordinary `[[ == ]]` semantics where `*` spans directory separators. This is
  more general than a basename filter and was necessary for `lint-task-lookup-adoption.sh`'s
  path-structured scope, but it also means a loosely-written pattern can over-match across
  directory depth -- see the `agents/` deep-nesting bug below.
- Each of the 6 affected lints is gated on an "unmodified default scan + shared corpus
  available" condition before using the fast path; any explicit scan-path argument (standalone
  custom invocation, or a fixture test's scratch directory) always falls through to the
  pre-existing enumeration, completely unchanged. This was the simplest way to guarantee
  "preserve standalone invocability" and "preserve the find-based fixture fallback" without any
  special-casing inside the fallback branches themselves.
- `verify-deploy.sh` captures whether the real `gate-registry-lib.sh` loaded (vs. its own
  degrade-safe stub) via a flag read BEFORE any of its stub-assignment lines run (since after
  those lines, `declare -F` is unconditionally true either way). The shared-corpus wiring is
  gated on that flag, not on `declare -F` at the point of use -- otherwise a missing lib would
  silently produce an "available but empty" corpus (every lint sees it as present, scans zero
  files, reports a false clean pass) instead of correctly falling back.

## What NOT to Try

- Do not write a shared-corpus filter pattern like `'agent-system/extensions/*/agents/*.md'` and
  assume it is scoped to one directory level. `*` in bash's `[[ == ]]`/`case` pattern matching
  spans `/` freely, so that exact pattern ALSO matched
  `lean/context/project/lean4/agents/lean-implementation-flow.md` (and one sibling file) -- a
  deeply-nested, unrelated directory that happens to be named `agents`. This was caught as a
  423-vs-425-file discrepancy when comparing the shared-corpus path against
  `lint-task-lookup-adoption.sh`'s own `collect_scan_files` baseline on the REAL corpus, not by
  inspection. The fix was an exact structural second pass (strip the extension prefix, take
  exactly the first remaining path segment as the extension name, require the remainder to match
  exactly `commands/*.md`|`skills/*.md`|`agents/*.md`|`scripts/*.sh` minus tests/deprecated) --
  see `lint-task-lookup-adoption.sh`'s shared-corpus branch for the working pattern. Any future
  shared-corpus consumer with a multi-segment scope should use the same structural-check approach,
  not a bare multi-segment glob, and should verify file COUNTS against the real corpus (not just
  a small synthetic fixture) before trusting a glob pattern is correctly scoped.
- Do not test the shared-corpus fallback path (no env vars set, default no-args invocation)
  against a synthetic/throwaway repo by just `cd`-ing into it before invoking the lint script.
  Every affected lint resolves its own `PROJECT_ROOT` from `$SCRIPT_DIR` (`${BASH_SOURCE[0]}`'s
  own on-disk location), not from the caller's cwd, so a `cd` has no effect on that resolution.
  Test the fallback path either with an explicit scan-path argument (the `find`-based branch,
  what every existing fixture test already does) or by copying the lint script itself into the
  synthetic tree at the matching relative path.

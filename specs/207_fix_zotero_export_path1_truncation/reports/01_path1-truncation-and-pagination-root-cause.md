## Executive Summary

- The dispatch's diagnosed accumulator bug (MAX_ARG_STRLEN, confirmed: `getconf ARG_MAX` = 2097152 but the actual per-argument cap that bites here is 131072 bytes = 128KiB, matching the script's own comment) is real and reproducible-by-inspection; fix direction (temp-file accumulation, `jq -s 'add'`) is straightforward.
- **The absorbed 208 "481-vs-4042" pagination discrepancy is now fully explained empirically, live against the running API**: it is a *third*, previously-unidentified bug, independent of the accumulator bug. Zotero's local API's `format=csljson` conversion silently **drops "annotation"-typed items from the returned page body** while still counting them in `Total-Results` and in the pagination window math — so a mid-library page can legitimately return fewer than `limit` items even though more pages remain. `fetch_path1()`'s termination check (`page_len -lt limit`) treats any short page as end-of-pagination, which is simply the wrong signal for this format. This is not a hypothesis: reproduced live, page-by-page, against the real API (see Findings).
- **A fourth, previously-unknown, and more serious defect was found**: the dispatch's own existing per-page filter (`select((.type // "") != "attachment" and (.type // "") != "note")`, work item 1's "retain the existing filter") is a **complete no-op** against Zotero's real CSL-JSON output — Zotero's csljson serializer never emits the literal strings `"attachment"` or `"note"` in the CSL `.type` field; it maps attachments to CSL type `"document"` (1821 of 3372 converted entries in this library — over half). Verified live: filtering with the existing predicate removes exactly 0 items.
- **A fifth, independently verified, out-of-file-but-same-function defect**: `fetch_path3()`'s bibliographic-only filter, `WHERE it.itemTypeID NOT IN (1, 3, 28)`, excludes the wrong Zotero itemTypeIDs entirely. The real IDs for `attachment`/`note`/`annotation` in this Zotero installation are `2`/`26`/`37`; IDs `1`/`3`/`28` are `artwork`/`audioRecording`/`podcast`. Since this library has virtually none of those three types, the filter is effectively a no-op: Path 3's exclusion-filtered count (4042) is **identical** to the completely unfiltered raw item-table count (4042), both including all 1770 attachments + 670 annotations + 46 notes alongside the 1556 true bibliographic items. **The dispatch's stated "ground truth," the current on-disk 4042-item export, is contaminated with non-bibliographic stub entries** — this changes what "parity" and "shrink guard baseline" should mean.
- Recommend: planner must decide how to scope the Path 3 itemTypeID fix (same file, adjacent function, but not named in the dispatch's work items) and must not set "Path 1 output count == 4042" as a Path-1-parity acceptance target, since Zotero's own local API structurally cannot return annotation-typed rows in `format=csljson` bodies (ceiling ~3372 raw-converted, ~1556 truly bibliographic after a *working* filter) — parity with the *current* Path 3 number is unreachable and undesirable.

## Findings

### Codebase Patterns

- `zotero-generate-export.sh` (583 lines) has three fetch paths (`fetch_path1`, `enrich_path2`, `fetch_path3`) plus a shared `synthesize_citekeys()` and atomic `write_output()`/`write_meta_stamp()` (temp-file + `mv`, already atomic — good precedent to follow for the accumulator fix and any shrink-guard read).
- The accumulator bug is exactly as diagnosed: `agent-system/extensions/literature/scripts/zotero-generate-export.sh:258` — `all_items="$(jq -n --argjson a "$all_items" --argjson b "$filtered" '$a + $b' 2>/dev/null || echo "$all_items")"`. Confirmed `MAX_ARG_STRLEN` on this machine via `getconf ARG_MAX` = 2097152 (2MB, the aggregate cap) vs. the actual single-argument cap (kernel constant, not queryable via `getconf`) of 128KiB = 131072 bytes, matching the script's own comment and the dispatch's instrumented trace.
- The sibling-accumulator sweep result stated in the dispatch (only line 258 is a genuine argv-accumulation instance; `synthesize_citekeys()`'s line 484 pipes the growing value via stdin and is a different, out-of-scope O(n²)/error-swallowing issue) was independently re-read from the current file and confirmed structurally correct — not re-verified by re-running the full sweep (per the dispatch's "already-verified, do not re-run" instruction).
- `--force` (lines 104, 127-130, 170-175) is the *only* existing flag, and it gates the "output already exists" pre-check (exit 3) before any fetch happens at all. It has no interaction today with item counts — it does not know what the new file *would* contain, only that a file exists. A shrink guard therefore needs to run **after** a candidate `ITEMS` array is fetched but **before** `write_output()` is called (line 574), comparing the candidate count against the existing file's count (or its `.zotero-library.meta.json` `item_count` stamp) — `--force` cannot be reused as-is because `--force` is required just to reach the fetch step when a file already exists; conflating the two would make the shrink guard impossible to bypass independently of the "already exists" bypass. The dispatch already flags this; confirmed by re-reading the arg parser.
- `write_meta_stamp()` (lines 501-526) already records `item_count` in `.zotero-library.meta.json` next to the output — this is the natural source for "previous count" without re-parsing the (potentially large, ~2MB) `zotero-library.json` itself.

### External Resources / Live API Measurement

All of the following was measured directly against the running local Zotero 7 API (`127.0.0.1:23119`), library size 4042 raw item-table rows (`Total-Results` header, identical for both `format=csljson` and default `format=json`):

1. **Raw (`format=json`, default) pagination is well-behaved**: every page from `start=0` to `start=3900` returned exactly `limit` (100) items; only the true last page (`start=4000`) returned the remainder (42), and `start=4100` returned 0. `Total-Results: 4042` matches exactly (`4000 + 42`).
2. **`format=csljson` pagination is NOT well-behaved by page-length**: at the identical `start` offsets, csljson page lengths were irregular and often far short of `limit` well before the true end — e.g. `start=400` -> 81, `start=500` -> 17, `start=600` -> 38, `start=700` -> 8, `start=800` -> 7, `start=900` -> 40, `start=1000` -> 10, `start=1100` -> 22, recovering to full 100-item pages again from `start=1700` onward, and genuinely ending only at `start=4100` (len 0; `start=4000` -> 42). Root cause, confirmed by exact-count matching: **each window's raw item mix includes some number of `annotation`-typed rows, and Zotero's csljson serializer drops those from the page body without adjusting `Total-Results` or the pagination window** (verified exactly at `start=400`: raw window type breakdown = 19 annotation + 54 attachment + 8 book + 3 bookSection + 10 journalArticle + 2 note + 4 preprint = 100; csljson page length = 81 = 100 − 19).
3. This is precisely what produced the dispatch's reported "terminates at 481 items" observation: `400 (start) + 81 (page_len at that start) = 481`, and `81 < limit(100)` trips `fetch_path1`'s existing `page_len -lt limit` break condition, which is simply the wrong end-of-pagination signal for this format.
4. **Correct termination signal, verified**: loop `start += limit` unconditionally (ignore the converted page's length for loop control) until `start >= Total-Results` (obtained once, e.g. from the first page's `Total-Results` header, or independently corroborated via the `Link: rel="last"` header, which for this library gives `start=4000` — consistent). Driving the loop this way for real, end to end (41 requests), reached the true end and summed to **3372** total csljson-converted items across the whole library (this already reflects Zotero's own silent annotation-drop; it is the ceiling Path 1 can ever reach as currently implemented against this API, regardless of any fix to the accumulator or the loop-termination logic).
5. **The existing "attachment/note" per-page filter is a verified no-op.** `zotero-generate-export.sh:256`'s predicate checks CSL `.type` for the literal strings `"attachment"`/`"note"`. Zotero's csljson serializer never emits those strings; the actual CSL `.type` distribution across the full 3372-item sweep was: `document` 1821, `article-journal` 1024, `book` 279, `chapter` 145, `article` 44, `paper-conference` 36, `thesis` 12, `manuscript` 4, `webpage` 2, `report` 2, `personal_communication` 2, `entry-encyclopedia` 1. Applying the existing filter to every one of the 41 pages live removed **exactly 0 items** (filtered sum == unfiltered sum == 3372, both measured). The 1821 `document`-typed entries are very likely a mix of standalone attachments (1770 raw attachment rows exist) and possibly other non-bibliographic content, since CSL-JSON's `document` type is Zotero's fallback mapping for its own `attachment` itemType. **A correctly working Path 1 filter cannot rely on the CSL `.type` field alone** — it needs either (a) a parallel raw-format (`format=json`, no csljson) fetch per page to read the authoritative `data.itemType`, cross-referenced by item key, or (b) a working server-side `itemType` exclusion query. Ad hoc testing of `itemType=-attachment%20-note%20-annotation` as a single query parameter did **not** work as hoped (a raw-format fetch with that filter still returned attachment- and note-typed rows in the result body), so the exact multi-exclude query syntax Zotero's local API expects is unverified and should be nailed down at implementation time against the official Zotero API docs' `itemType` grammar, or option (a) taken instead.
6. **Path 3's bibliographic-only filter is also a verified no-op, for a different reason, with a materially larger effect.** Read the live `itemTypes` table (via `sqlite3 "file:<path>?immutable=1" ...`, since a normal `-readonly` connection reports "database is locked" while Zotero is running): real IDs are `attachment=2`, `note=26`, `annotation=37`. `fetch_path3`'s `WHERE it.itemTypeID NOT IN (1, 3, 28)` excludes `artwork`/`audioRecording`/`podcast` instead — types this library has ~0 of. Confirmed by direct count: `... NOT IN (1,3,28)` = 4042 = the completely unfiltered `count(*)` for the user library; `... NOT IN (2,26,37)` (the correct IDs) = **1556**, the true bibliographic-item count (1024 journalArticle + 279 book + 145 bookSection + 44 preprint + 36 conferencePaper + 12 thesis + 5 document + 4 manuscript + 2 webpage + 2 report + 2 letter + 1 encyclopediaArticle).
7. Consequence of finding 6: the dispatch's "reference point" — "Path 3 ... produced a complete, verified 4049-item export matching `select count(*) from items` exactly" — is accurate as literally stated (it matches the *unfiltered* total), but that total is not a bibliographic-item count; it is contaminated with 1770 attachment-stub entries, 670 annotation-stub entries, and 46 note-stub entries carried through `fetch_path3`'s CSL-shaping `jq` (which will produce entries with empty/garbage `title`/`author`/`issued` fields for most of these, since attachments/annotations have no such Zotero metadata fields populated). The on-disk `zotero-library.json` that the shrink guard is meant to protect is, right now, ~61% non-bibliographic stub entries.

### Recommendations

1. **Accumulator fix**: implement per the dispatch exactly as specified (per-page temp files + `jq -s 'add'` once at the end; no argv growth). No new information changes this.
2. **Pagination-termination fix (absorbs the 208 acceptance criteria)**: replace the `page_len -lt limit` break condition with a `Total-Results`-driven loop (`start += limit` unconditionally; stop when `start >= total`, where `total` is read once from the `Total-Results` response header of the first request). Distinguish three terminal states explicitly, per work item 2's instruction: (a) genuine end (`start >= total`), (b) `max_pages` guard hit, (c) a request/parse error (abort loudly, no write) — none of these should be conflated with "short page," since short pages are now known to be a normal, expected mid-pagination occurrence for this format.
3. **Filter fix**: the planner must choose between (a) a parallel raw-format lookup per page to get authoritative `itemType` and drop non-bibliographic keys before/after CSL conversion, or (b) find and verify the correct server-side `itemType` exclusion syntax against Zotero's actual API grammar (not guessed ad hoc as this research session tried). Either way, the **existing filter predicate must be treated as already broken**, not merely "retained" — silently keeping a no-op filter would ship ~1800 `document`-typed junk entries into every future Path 1 export.
4. **Decision needed from planner/user on Path 3's itemTypeID bug (finding 6/7)**: it lives in the same file and same general area (`fetch_path3`, lines 335-378) as this task's declared scope, but is not named in any of the dispatch's work items, and fixing it would change the on-disk "ground truth" the shrink guard compares against (from 4042 down to ~1556, a >60% drop that the shrink guard itself would otherwise flag as catastrophic). Recommend surfacing this explicitly as a **user-decision point** in planning: fix it now (same task, same file, directly relevant to what "correct" means for both the shrink guard and the absorbed-208 parity criterion) versus spin it out as a separate follow-up task (keeps this task's blast radius smaller, but ships/documents a shrink guard whose baseline is knowingly wrong, and leaves the absorbed-208 acceptance criterion #2 — "a full export via Path 1 matches the sqlite-reconstruction item count" — either unattainable (3372 vs 4042) or misleadingly "satisfied" only if Path 3 is also fixed to the true 1556).
5. **Shrink-guard baseline**: whichever way finding 6/7 is resolved, the guard's "previous count" should read `.zotero-library.meta.json`'s `item_count` (already written by `write_meta_stamp()`) rather than recomputing from the full JSON file, and should compare it against the newly-fetched candidate's count before `write_output()` is called (line ~572-574), not after.
6. **Regression test mechanism (work item 4)**: `agent-system/extensions/literature/scripts/tests/curl-stub.sh` is a viable base but needs real extension, not just a new case branch:
   - It dispatches purely on **hostname** substring match (`*api.semanticscholar.org*` etc.). `zotero-generate-export.sh`'s two relevant endpoints — the items API (`.../api/users/0/items`) and the Better BibTeX RPC (`.../better-bibtex/json-rpc`) — share the **same host:port** (`127.0.0.1:23119` / `localhost:23119`), so the stub must add **path-based** dispatch, not just a new host case, or BBT-RPC calls will be misrouted into the items handler.
   - The stub's two recognized curl invocation shapes (`-w '\n%{http_code}'` combined, or plain body-only) do not cover `probe_zotero_api()`'s exact invocation: `curl -s -o /dev/null -w '%{http_code}' ...` (no leading-newline format, and the body is discarded by `-o /dev/null` so the stub must not print a body at all in that case — it must print only the code). This needs a third recognized shape.
   - `fetch_path1()`'s own per-page GET (`curl -s --connect-timeout 2 --max-time 20 "${API_BASE}?format=csljson&limit=...&start=..."`) matches the already-supported "body only" shape, so the stub's job there is generating **synthetic paged bodies large enough to cross 128KiB** and, ideally, a scenario that also reproduces finding 2 (a short mid-pagination page) so the termination-logic fix has its own dedicated regression case distinct from the accumulator-boundary case.
   - The stub will need to parse `start=`/`limit=` from the query string (it currently does no query-string parsing at all — only whole-URL substring matching) to serve the correct synthetic page and to emit the right `Total-Results`/`Link` response headers (which the stub also does not currently emit at all — it prints body/code only, via `printf`, with no header simulation route). Since `curl -sD -` header capture isn't how `zotero-generate-export.sh` reads `Total-Results` today (it doesn't — this is a *new* behavior this task is adding per recommendation 2), the implementer will need to decide how the fixed script reads that header (e.g. `curl -sD - -o body_file ...` to capture headers and body separately) and make sure the stub can emit a matching `Total-Results:`/`Link:` header block for that invocation shape too.
7. **Doc updates (work item 5)**: `zotero-pdf-resolution.md` already has a precedent section (lines 34-55, 101-102) documenting a different *known, latent* `fetch_path3()` bug (hardcoded `$HOME/Zotero/storage/...` ignoring a custom Data Directory) using "known, latent, not yet fixed, recorded here as a follow-up item" phrasing — this is a good template to reuse for whichever of findings 3-7 remain undone after this task's fix, and a natural place to *also* land the new finding about `fetch_path3`'s itemTypeID no-op if the planner spins it out rather than fixing it inline. `literature-index.md:206` and `corpus-directory-conventions.md:115` currently only note that `zotero-generate-export.sh` is "not applicable" to their respective concerns (id semantics; corpus directory conventions) — those single-line mentions likely just need their existing "not applicable" framing double-checked for continued accuracy, not a rewrite. `commands/literature.md` has substantial existing Path 1/Path 3 selection narrative (lines 130-360) that already describes `--force` auto-selecting Path 1 vs Path 3 and references the "never write an empty file, fail loudly instead" guarantee (line 355-357) — this is the file most likely to need real prose additions describing the new shrink-guard flag/behavior and the corrected pagination contract.

## Decisions

- Confirmed (do not re-derive): the accumulator bug (dispatch's primary diagnosis) is correct and independent of the pagination-termination bug (this report's finding 2/3) and the two itemType-filter no-op bugs (findings 5/6) — four separate, independently-verified defects in total, all touching `zotero-generate-export.sh`.
- Confirmed (do not re-derive): the absorbed-208 "481 vs 4042" question is answered — it is caused by treating short csljson pages as end-of-pagination, not by any limit/start-offset-vs-format-filtering-order ambiguity of the kind speculated about in the original task 208 text. None of task 208's three original "candidate directions" (csljson-format-filtering pre/post window, a general local-API pagination quirk, or attachments/notes/annotations inflating Total-Results) was the literal mechanism — the actual mechanism is closest to the third candidate but more specific: attachments/notes/annotations do inflate `Total-Results`/window math (relative to the true bibliographic count), but the acute, page-breaking symptom is annotations being silently dropped **from page bodies only**, which the original task 208 text did not anticipate.
- Not decided here (left for planning / user): whether to fix `fetch_path3`'s itemTypeID bug within this task's scope, given it is in the same file but outside the dispatch's named work items, and given it changes the shrink guard's own baseline assumption.

## Risks & Mitigations

- **Risk**: fixing only the accumulator (as narrowly read) without also fixing the pagination-termination logic would leave Path 1 silently capping out at whatever `start` value happens to hit a short annotation-heavy page next — i.e., still a silent-truncation bug, just at a different threshold than 128KiB. Mitigation: the dispatch's own absorbed-208 section already requires fixing this; this report gives the concrete, verified fix (Total-Results-driven `start` increment).
- **Risk**: shipping the shrink guard against the *current* contaminated 4042-count baseline could cause the guard to falsely treat a *correctly* filtered future Path 3 or Path 1 run (~1556 true bibliographic items) as a catastrophic shrink and block a legitimate, more-correct regeneration. Mitigation: surface finding 6/7 explicitly to the user/planner before finalizing shrink-guard threshold semantics.
- **Risk**: the itemType-filter fix (finding 5) could be implemented as a second, still-wrong ad hoc guess (e.g., trusting an unverified `itemType=-x -y -z` query syntax) and ship silently broken again. Mitigation: recommend the cross-reference-with-raw-format approach (definitely correct, verified data source) unless the correct server-side query syntax is independently confirmed against Zotero's official API documentation during implementation.
- **Operational note**: this research session opened the real Zotero application (per the dispatch's explicit precondition) to measure live API behavior, and closed it again afterward by `kill` (SIGTERM to the wrapper, launcher, and content processes) rather than a graceful in-app quit, since no GUI automation tool was available in this dispatch. The API was reconfirmed unreachable (HTTP `000`) afterward, and the on-disk export file and its meta stamp are unchanged (verified via checksum/re-read). A stale `zotero.sqlite-journal` may remain from the non-graceful shutdown; this is Zotero's own internal recovery artifact, unrelated to the repo or to `zotero-library.json`, and Zotero handles startup recovery from such journals automatically — flagged here for transparency, not as an action item.

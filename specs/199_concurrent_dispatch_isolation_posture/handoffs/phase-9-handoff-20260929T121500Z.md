## Key Decisions Made

- **Phase 7's isolation status is re-derived via `dispatch-worktree.sh path "$task_number"`**
  (exit 0 + path = isolated), never read off a dispatch-row field — this was the Phase 6
  handoff's own design correction and kept `orchestrate-cycle-postflight.sh`'s edit
  self-contained (no `skill-orchestrate/SKILL.md` Move 3 touch).
- **Phase 8's Group 31 discovered that `orchestrate-batch-admit.sh`'s PRE-EXISTING in_batch
  file_scope collision check already, unconditionally, defers one of any two same-cycle
  candidates whose declared `file_scope` entries are identical or in a true directory/ancestor
  relationship** — confirmed empirically (an earlier draft's fixtures for exactly those two
  shapes were silently reduced to 1-task cycles before ever reaching `build_contended_manifest`).
  That check has no override for in_batch pairs. The REAL, live-reachable gap
  `build_contended_manifest` closes is a GLOB entry, which is "invisible to the symmetric Overlap
  predicate by design" per `lib/file-scope-overlap.sh`'s own `is_glob_entry` comment — a
  glob-vs-concrete-path pair sails through admission un-deferred even though it genuinely
  contends. Group 31's Cases A/B use glob-vs-concrete fixtures for this reason; a standalone Case
  G unit-tests the directory-containment branch of `_paths_contend` directly (unreachable live,
  but must still be correct on its own terms — e.g. for a future admission-gate change, or a
  caller other than `orchestrate-cycle-plan.sh`).
- **Phase 9's claim mechanism reuses `task-lock.sh`'s `acquire_named_mutex`/`release_named_mutex`
  primitives directly**, via two new CLI subcommands (`claim-acquire`/`claim-release`, mirroring
  `commit-acquire`/`commit-release`'s exact shape) rather than a hand-rolled mkdir/staleness
  implementation inside `git-commit-scoped.sh`. `task-lock.sh` is NOT sourceable (bare CLI
  dispatch at EOF, not wrapped in a `main` function), so the shell-out convention
  (`bash task-lock.sh claim-acquire ...`) was used, matching the file's own existing
  `commit-acquire`/`commit-release` call pattern. `acquire_named_mutex`'s `mkdir` is NOT
  `mkdir -p` — `cmd_claim_acquire` must `mkdir -p specs/.contention-claims` once before calling
  it, or every acquire attempt fails closed looking identical to "held by someone else" (caught
  and fixed during manual smoke testing, not by the automated suite — see What NOT to Try).
- **`--task` was wired into exactly ONE real (non-test) caller**: `orchestrate-cycle-postflight.sh`
  WORK (i), the shared-tree per-cycle commit call this whole task's incident is about. The other
  two real callers (`orchestrator-postflight.sh`, the single-task engine's own commit;
  `orchestrate-unwind-dispatch.sh`, the rollback path) were deliberately left unwired — both
  remain fully fail-open/unchanged since `--task` is opt-in, and both are out of scope for the
  multi-task shared-tree scenario. This was NOT an explicit Phase 9 task-list bullet but was
  required by the phase's own Goal ("the SHARED-TREE COMMIT PATH") and Scope Hypothesis wording
  ("...or is updated deliberately in this phase") — recorded as a deviation in
  `progress/phase-9-progress.json`.
- **A test fixture pitfall worth knowing for Phase 10**: `orchestrate-cycle-postflight.sh` always
  resolves `STATE_FILE` to an ABSOLUTE path internally (`case "$state_file_arg" in /*) ... *)
  STATE_FILE="$PROJECT_ROOT/$state_file_arg" ;; esac`), so `specs/state.json` can never
  exact-string-match a manifest's own RELATIVE declared path. The Phase 9 wiring test uses the
  task's own `modified_files` entry (always relative) as the contended path instead — Phase 10's
  shared-tree fixture leg should do the same (contend on a declared `file_scope`/`modified_files`
  path, never on `specs/state.json` itself).

- Do not read isolation status off a dispatch-row field in `orchestrate-cycle-postflight.sh` —
  re-derive via `dispatch-worktree.sh path`, per the Phase 6 handoff's correction (Phase 7 already
  did this; a Phase 10/11 edit to the same script must preserve it).

  expecting them to reach `build_contended_manifest` live — `orchestrate-batch-admit.sh`'s
  pre-existing in_batch collision check defers one of them first. Use a glob-vs-concrete pair, or
  test the underlying predicate directly (Group 27/31's function-extraction precedent).
- Do not call `task-lock.sh`'s `acquire_named_mutex`/`release_named_mutex`-backed
  `claim-acquire`/`claim-release` subcommands without first ensuring
  `specs/.contention-claims/` exists (`cmd_claim_acquire` does this internally via `mkdir -p`,
  but a DIRECT call to `acquire_named_mutex` from new code would need the same guard — it is NOT
  `mkdir -p` on its own).
- Do not use `specs/state.json` (or any other path `orchestrate-cycle-postflight.sh` resolves to
  an ABSOLUTE path) as a contended-path fixture path expecting an exact-string manifest match —
  use a relative `modified_files`/`file_scope` entry instead.
- Do not re-run the full `bash .claude/scripts/tests/run-all.sh` deployed-tree baseline again
  before Phase 11's redeploy step — its 11 pre-existing failures are already recorded above;

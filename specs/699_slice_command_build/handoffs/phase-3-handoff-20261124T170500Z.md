## Key Decisions Made

- **`status` never writes the document and never refuses on check/build-style validation
  failures** — a deliberate asymmetry from `check`/`build`, since `status` must be usable to
  observe exactly the "stale" realities (target not an ancestor, base moved, remote diverged)
  that a caller needs reported, not blocked on.
- **The no-dependency static assertion excludes pure-comment lines** from its
  `review-stack-prepare` grep — see progress file deviation 3.5. The script's own explanatory
  comments correctly NAME the decision not to depend on that file; only an actual
  source/invocation would be a violation.
- **Remote-tracking-ref test fixtures use `git update-ref`, never `git push`** — see progress
  file deviation 3.1. `git push` is unconditionally guard-blocked in this environment even
  against a throwaway local bare/fixture repo with no network or forge involvement; `status`
  itself only ever reads `refs/remotes/<remote>/...`, so fabricating that ref directly is
  sufficient and exercises the exact same code path a real push-then-fetch would produce.

## What NOT to Try

- Do not try to exercise the "pushed" status cases via an actual `git push`, even to a local
  throwaway bare repo under `/tmp` — `guard-git-push.sh` blocks it unconditionally regardless of
  destination. Fabricate the remote-tracking ref directly with `git update-ref` instead.
- Do not make `status` write back to the document or refuse on a check-style validation
  failure — both would break its role as the reporting primitive `commands/slice.md`'s continue
  step needs.
- Do not expect `verify-touched.sh` over the two touched paths to pass cleanly before Phase 5/6
  — same pre-registration gap already logged against Phases 1 and 2 (non-blocking).

## Rulings Recorded by This Plan

These are the dispatch's four decision demands, settled here so implementation transcribes rather
than re-decides. Each is also written into a deliverable, as noted.

1. **Parentage is not a dependency.** `parent_task` is a lineage pointer recording which task a
   follow-up or spawned task came out of. A parent may reach a terminal status before any child
   does; a child is dispatch-eligible regardless of its parent's status. Nothing reads
   `parent_task` when computing dependency waves. *Written into*: the schema `description` (Phase
   1) and the `### Parent Task Field` doc section (Phase 3).

2. **Rendering: per-task TODO.md line, never the Task Order tree.** Parentage renders as a
   `- **Parent**: Task {N}` line in the per-task TODO.md entry, immediately after
   `- **Dependencies**:`, and is **omitted entirely** when the field is absent.
   *Rationale for the exclusion*: `generate-task-order.sh`'s indentation channel is already
   pre-committed to dependency semantics by its own two display strings ("Grouped by Topic
   (indented = depends on parent)" and "Dependency Tree (indented = depends on parent)"). Putting
   a second, different relation into the same visual channel would make every indent ambiguous
   between "depends on" and "descends from", and the word "parent" in those strings already means
   the dependency-graph parent. The Task Order tree therefore renders **no** parentage at all.
   *Written into*: the `### Parent Task Field` doc section's Format Conversion table plus an
   explicit "not rendered in the Task Order tree, and why" note (Phases 3 and 6).

3. **An archived parent is expected, not a finding.** The orphan check's known-number set unions
   `active_projects` with the sibling `archive/state.json`'s terminal arrays — exactly the
   existing `dependencies` dangling-reference precedent in Check D3. A parent found in the archive
   is normal settled lineage. Only a parent absent from **both** is an orphan (WARN). Parent/child
   *status* combinations are never examined: a `not_started` or `blocked` child under a still-active
   parent is ordinary mid-lifecycle parentage and must never be flagged. *Written into*: the Check
   D6 header comment and the doc section's Validation bullets (Phases 3 and 4).

4. **Renumbering is a live path, and it is the prose checklist.**
   `scripts/deprecated/vault-operation.sh` stays quarantined — its own `scripts/deprecated/README.md`
   records zero live callers plus an unmutexed-`state.json`-write reactivation hazard, so
   reactivating it is wrong independent of this task. The live renumber path is `commands/todo.md`
   Step 5.7.7, whose 5-item checklist rewrites `dependencies` arrays but has no step for
   `parent_task` — so a vault operation would today silently dangle every parentage edge. That is
   fixed by adding a sibling sub-step to the live checklist. *Written into*: `commands/todo.md`
   Step 5.7.7 and the doc section (Phase 7).

## Rollback/Contingency

Every phase is a small, independently revertible commit over source-store text files, and no
phase writes to `specs/state.json`, so an ordinary `git revert` of the offending commit restores
the prior state with no data-migration concern.

Two orderings matter if a partial rollback is needed:

- Phase 1's two files must revert together, or the drift test goes red. Revert that commit whole
  (it is `atomic-batch` precisely so this is possible).
- Phase 4's Check D6 can be reverted on its own, but Phase 5's cases will then go red; revert both
  or neither.

If a genuine working-tree rollback becomes necessary — discarding uncommitted edits rather than
reverting a commit — take the snapshot first per `context/contracts/recovery.md`'s rollback rung,
using the invocation shape recorded there (including its out-of-scope override flag if the revert
must span files outside this task's `file_scope`). Do not take a bare reverting snapshot as a
routine start-of-phase precaution; for an ordinary defensive checkpoint before a risky edit, use
the non-reverting `--no-revert` form instead.

Because four sibling tasks share this working tree this cycle, any rollback must be scoped to
this task's own files by explicit path list — never a directory or glob pathspec, and never a
whole-tree reset.

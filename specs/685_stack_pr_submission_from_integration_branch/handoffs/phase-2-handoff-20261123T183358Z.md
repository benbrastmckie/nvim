## Key Decisions Made

- **Selection is gathered (not validated) before review_base/remote/platform resolution.**
  `rsp_gather_selection` (never refuses) runs first so the integration-branch resolver has
  selected tasks to look up when there are any; `rsp_validate_selection` (refuses 40/41/42) runs
  only inside `rsp_cut_build_and_print`, after review_base/remote/platform are resolved. This
  keeps every one of Phase 1's refusal-path assertions reachable with `cut --dry-run` and no
  selection at all -- the first draft validated selection immediately and broke all of them.
- **Five Phase 1 success-path assertions were moved from `cut` to `show`.** They test the shared
  resolver chain (a valid `--review-base` override, GitHub platform detection, the three remote-
  resolution branches), not `cut`'s own body, and `cut --dry-run` with no selection now refuses
  (by design, Phase 2's whole point). `show`'s body is still the Phase 1 placeholder, so it still
  prints the old `review_base='...' remote='...' platform='...'` line these assertions grep.
- **The "earlier unmerged task" refusal branch (pull in when selectable, else refuse naming
  both) has no suite case.** Every landing-proof entry `rsp_detect_pulled_in` finds is, by
  construction, resolvable (it already carries `task_number`, `end_commit`, `paths`), so the
  refusal path is reachable only by a malformed proof -- not exercised here, and not in the
  plan's own listed suite cases for this phase. Noted as a follow-up for Phase 3/7, not treated
  as a gap in the pull-in mechanism itself (which does have a passing case).
- **Branch slug for a merged unit is the lowest member task's slug**, not a combination of every
  member's. The plan names "the task slug" singular; this is the simplest reading and avoids an
  unbounded branch-name length for a unit with several members.
- **`--order`'s current implementation treats the whole selection as one chain**, overriding
  every component into a single ordered sequence. This is simpler than preserving multiple
  independent chains under an operator order and matches the plan's own flag description
  ("an operator order"), but is untested; a future phase relying on `--order` across several
  components should add a case first.

## What NOT to Try

- Do not validate cut's selection (40/41/42) before resolving review_base/remote/platform --
  this was tried and reverted; it breaks every Phase 1 refusal-path assertion that calls `cut`
  with no selection to exercise those resolvers directly.
- Do not assume `git merge-base --is-ancestor` orders two commits made in quick succession by
  wall-clock time; it orders by actual ancestry on the branch. The suite's "landing order"
  fixtures control this by controlling commit SEQUENCE (which commit is made first), not by
  setting timestamps.

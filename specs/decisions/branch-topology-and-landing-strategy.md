# Decision Record: Branch Topology and Landing Strategy

This record rules on branch granularity, merge strategy, landing mechanics, and worktree
isolation for orchestrated work in this repository, re-opening and re-settling the question
`branch_aware_orchestration_and_squash_landing` had called settled. The aim stated for the
reopening is the highest-quality, most-seamless workflow with minimal churn, working off a
long-lived feature branch with side branches and squash merging as appropriate, with milestones
as the natural review points.

Decided 2026-11-20 by `branch_topology_ruling_and_milestone_automation` (657). Tasks are named by
slug with the number alongside, because numbers are reassigned at a vault renumber and slugs are
not.

## Rulings

| # | Ruling | Basis | State change |
|---|--------|-------|---------------|
| R1 | The hot-path branch is whatever single branch is already checked out, verified rather than assumed at admission time. No branch is created during dispatch work at any granularity (not per invocation, per task, or per milestone). | `grep -rn "git checkout -b\|git switch -c"` across the core extension's `scripts/` and `hooks/` returns exactly one hit (`git-snapshot.sh`'s `--branch` rollback path, a recovery feature, not a workflow); every phase commit today lands on whatever branch the operator left checked out, and this ruling keeps that the explicit design rather than a latent accident. Creating a branch on the hot path reintroduces the `checkout` hazard against the one shared working tree every concurrent session mutates. | None at this task; `branch_aware_orchestration_and_squash_landing` (655)'s Element A admission-time check (that the checked-out branch matches a declared integration branch) is unchanged by this ruling. |
| R2 | A milestone's review history is built by ref plumbing — `git commit-tree` plus compare-and-swap `git update-ref` — never by `checkout` or `git merge --squash`. One squash commit is appended to `refs/heads/milestone/<id>` per completed task, with `<id>` resolved from `roadmap_milestones[].id`, never a literal milestone name. | `git commit-tree` and `git update-ref` touch neither the working tree, the index, nor `HEAD`. A concurrent sibling dispatch in the same shared tree is structurally unaffected by a landing operation built from these two primitives, because neither reads nor writes any of the three things a concurrent dispatch depends on. | `agent-system/extensions/core/scripts/milestone-ref-land.sh` (new, Phase 3). |
| R3 | Merge strategy is squash per task, landed onto the milestone ref. Whether the milestone ref is itself squashed again when it ultimately merges into the long-lived integration branch is left to the human reviewer's judgment at review time. No automatic rebase of a milestone ref onto a moved integration-branch tip is built. | Squash-per-task is the short-lived-unit squash convention this system already uses for phase commits and that `branch_aware_orchestration_and_squash_landing`'s prior design endorsed; only the landing *mechanism* changes under R2, not this choice. A milestone ref that has drifted far behind a fast-moving integration branch produces a noisy review diff, but resolving that automatically requires rewriting history on a ref a human may already be reviewing — explicitly left to human judgment rather than built. | None; a design non-goal recorded in the implementing plan. |
| R4 | The integration-branch declaration's key name and shape are fixed here: a `.claude-extensions.json` top-level key (per `repo-level-declarations.md`'s existing home for a per-repository declaration), consumed by this task's scripts with a loud, named advisory fallback to the currently checked-out branch when the key is undeclared. The schema row in `context/standards/repo-level-declarations.md` and the admission-time assertion that the checked-out branch matches the declared value belong to `branch_aware_orchestration_and_squash_landing` (655), not to this task. | Keeping the schema write and the admission-time assertion off this task's `file_scope` (`repo-level-declarations.md` is not among this task's touched paths) avoids duplicating 655's declared territory, and `commit-layer-cluster-ordering.md`'s Edge row for `stage_regenerated_derived_files_in_phase_commits` (517) already names "655 adds a declaration schema to `repo-level-declarations.md`" as its own falsification condition — this ruling triggers exactly that condition. | 655 gains 517 as a predecessor (Phase 2, Edges section below). |
| R5 | Worktree isolation is NOT reinstated, in any form, at any granularity. | **Binding evidence engaged by name.** `specs/decisions/worktree-isolation-removal-verdict.md` and `specs/decisions/worktree-isolation-removal-reaffirmation.md` record four measured defects, all induced by the layer itself, not by anything external to it: (1) destructive release on a `nothing_to_land` verdict that nearly destroyed 456 verified Lean lines; (2) `git-commit-scoped.sh`'s worktree-blind `PROJECT_ROOT` silently dropping every pathspec to a false-success WARN-and-drop; (3) `lake-build-guard.sh`'s shared-inode false green from `cp -al`-cloned state files; and (4), found on reaffirmation, postflight marking both of two tasks `completed` while 18 and 10 commits respectively sat stranded on unmerged branches with one task's entire output absent from `main` — silent non-landing of *committed* work under a `completed` status, a broader hazard class than defect (1)'s uncommitted-work framing. The structural reason named across both records is that hardlink-clone correctness depends on "independently rebindable via atomic rename," a **per-writer** property, not a property of the clone — so a layer built on it cannot be audited once and trusted; every script with mutable per-invocation state inside the cloned tree is a fresh instance of the hazard, closed only by a hand-maintained exclusion list. The reaffirmation record additionally evaluated CoW/reflink (unavailable: this repository's root filesystem is `ext4`, no `FICLONE` support, and a filesystem migration is out of scope) and overlayfs (structurally correct but requires privileged mount management per worktree, a new infrastructure class, and does nothing for the independently-found repo-scanning-pollution hazard) as candidates that could dissolve the per-writer hazard, and found neither a drop-in fix available today. This design proposes no resurrection, so none of that evaluation is reopened; it is cited to show the question was engaged, not skipped. **Why this design cannot reproduce the recorded mechanism.** Ref plumbing (R2) creates no clone of mutable state at all — `git commit-tree` reads objects already in the object database and writes a new, immutable commit object; `git update-ref` moves a ref pointer. There is no shared inode between a landing operation and any other script's state files, and therefore no exclusion list for an unrelated script to miss — the exact shape of defects (2) and (3). Defect (4), non-landing under a reported-complete status, is closed structurally by Phase 4's design: the landing and its `--verify` mode run, and are confirmed to have succeeded, strictly *before* the completion-status write, with the write refused (not skipped silently) on failure — the inverse of postflight's prior behavior of writing `completed` regardless of landing outcome. Defect (1), destructive release of uncommitted work, has no counterpart here because nothing is released: a milestone ref, once advanced, is never torn down by this design except by an explicit, human-initiated `git update-ref -d`. The repo-scanning-pollution hazard found on reaffirmation (worktree directories double-counted by tree-walking tools) has no counterpart either, because no worktree directory is created. | None; a design non-goal recorded in the implementing plan, and ruling R6 below records the premise this holds. |
| R6 | The one-HEAD-per-repository premise holds under this ruling, so `phase_commit_boundary_mechanical_check` (513)'s expected-ref parameter stays per-repository rather than becoming per-tree, and the dispatch's `CONDITION ON A RULING` does not fire. | Ruling R5 reinstates no form of tree isolation; every dispatch continues to run in the repository's single working tree with one `HEAD`. `commit-layer-cluster-ordering.md`'s Judgment 1 names exactly this condition ("a 657 ruling that reinstates any form of tree isolation" as what would change its ruling that source-store commit scoping and the third containment site are not hard prerequisites for branch-aware orchestration) — this ruling does not trigger it. | None; a confirmation recorded in Phase 2 rather than left implicit (see `### Premise Re-Validation` item 10 of the implementing plan). |
| R7 | `orchestrate-conclusion-roadmap.sh`'s existing unconditional Move 4 regenerate of `specs/ROADMAP.md` already satisfies Element 2's "an orchestration completing updates its milestone's progress and regenerates ROADMAP.md" bullet, and `orchestrate-batch-gate.sh`'s existing once-per-invocation complete-gate run (triggered whenever any implement dispatch occurred) already satisfies Element 2's "a batch's orchestrations all completing initiates systematic testing" bullet. No parallel path is built for either. | Both call sites were read directly rather than assumed from the research report's summary: `orchestrate-conclusion-roadmap.sh` regenerates `ROADMAP.md` unconditionally at every invocation's Move 4, and `orchestrate-batch-gate.sh`'s "any implement dispatch happened" trigger is a safe superset of "every batch member reached a terminal status" for the purpose of initiating testing — narrowing it to batch membership would cost a new read of `roadmap_milestones[].batches[]` at a call site that uses no milestone data today, for strictly less testing coverage, and is declined as a non-goal. | None; both are confirmations, not new code. |
| R8 | The milestone-completion step PREPARES the push and the review request and hands them to the user through the existing `/please` + `/merge` consent-gated path. It never mints a grant, never infers permission from a milestone reaching completion, and never pushes or opens a PR/MR autonomously. This is a deliverable property of the design, stated explicitly, not an implementation detail left to be inferred. | `rules/pr-prohibition.md` bars agents from pushing and from creating PRs/MRs, with a single scoped exception: a human-invoked `/please <push request>` mints a single-use HMAC-signed grant (`hooks/please-grant.sh`) that `hooks/guard-git-push.sh` admits and `scripts/git-push-granted.sh` consumes. The archived task `consent_gated_git_push` built this end to end; this design is forbidden from duplicating it and is instead a producer of the literal commands a human types into that existing path. `hooks/guard-git-push.sh` mechanically refuses an unguarded push regardless of what this design does, so the property is both a design commitment and independently enforced. | `agent-system/extensions/core/scripts/milestone-review-handoff.sh` (new, Phase 5): writes `review.state`/`review.ref`/`review.updated` and a draft handoff file; prints the literal `/please` and `/merge` commands; calls none of `git push`, `git-push-granted.sh`, `gh`, `glab`, or `/merge`. |

## Edges

Exactly one new dependency edge is justified by this ruling, and it is written in Phase 2, not
here: `branch_aware_orchestration_and_squash_landing` (655) gains
`stage_regenerated_derived_files_in_phase_commits` (517) as a predecessor, under ruling R4 and
the falsification condition `commit-layer-cluster-ordering.md` already names for 517 (see that
record's Rulings table entry for 517).

The `657 -> 553` (`git_commit_scoped_gate_refusal_diagnostic`) candidate the task 657 dispatch's
own `ORDERING` block and the research report's Element 2 recommendation both proposed is
**not written**. That edge was already deliberately moved off this task and onto 655 in
`commit-layer-cluster-ordering.md`'s Edge 6, for the reason that record's own "Why edge 6 sits on
655 and not on 657" paragraph gives: parking this task's ruling (which edits no shared script)
behind the full ten-task commit-layer chain buys no protection for the landing commit the chain
actually threatens, since 655 — which does edit the shared scripts — remains fully ordered
behind 553 regardless. Re-adding it here would reverse that remedy for no gain. Live state at
authoring time: 657's `dependencies` are `[654, 656]` (no 553); 655's are
`[513, 553, 654, 657]`.

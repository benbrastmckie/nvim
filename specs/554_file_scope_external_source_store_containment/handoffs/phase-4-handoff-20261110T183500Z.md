## Key Decisions Made (including a bug found and fixed)

- **Bug found and fixed in Phase 1's own library** (`source-store-path-lib.sh`): the SOURCE_STORE
  attribution branch originally emitted the fourth field relative to `source_dir`, not relative
  to `source_toplevel` as the library's own documented contract requires
  (`SOURCE_STORE<TAB><extension><TAB><source_toplevel><TAB><path_relative_to_that_toplevel>`).
  This surfaced only when Phase 4's end-to-end test attempted to actually `git add` the emitted
  path inside the second repository and got "file does not exist" -- the path was one directory
  level too short. Fixed by emitting the tested path's own string unchanged for the relative
  shape (since, by the universal spelling convention, a path already relative to the consumer's
  root is simultaneously valid relative to source_toplevel) and by computing the absolute shape's
  relative-to-toplevel path directly via `realpath --relative-to`. `test-source-store-path-lib.sh`
  Cases 1 and 2 were corrected to match the documented (and now actually-implemented) contract.
- `commit-source-store-path.sh`'s own exit-code vocabulary is deliberately distinct from, and
  never compared against, `git-commit-phase.sh`'s own -- the wiring only inspects 0/1/other.

## What NOT to Try

- (Carried) Do not resolve a relative path's parent directory without anchoring at the passed
  `repo_root` first.

  relative to `source_toplevel`, or `commit-source-store-path.sh` cannot resolve the file on
  disk.

## Key Decisions Made

- The project-key resolution path is duplicated directly into `postflight-sapience-notes.sh`
  (copying `sapience-remember.sh`'s own PROJECT-KEY RESOLUTION block: `resolve_checkout_toplevel`,
  host/token precedence, binding-cid match) rather than adding a resolve-only flag to
  `sapience-remember.sh` itself, because that script is outside Phase 4's declared `Files to
  modify`. The duplicate is deliberately NOT added to the `sapience-worktree-checkout-resolution`
  marker block's tracked nine-file lockstep set
  (`test-sapience-mcp-registration.sh` Case 30) — the two copies are intentionally independent.
- On a resolution FAILURE (binding present but the GET fails or matches no entry),
  `postflight-sapience-notes.sh` omits `--project-key` from every per-note call, so each
  `sapience-remember.sh` invocation still attempts its own per-call fallback resolution
  (unchanged pre-Phase-4 behavior). The "resolve once" guarantee is therefore EXACT for the
  success path (the one the plan's Verification criterion actually names and this phase's new
  Case 10 tests) and a best-effort improvement on the degrade path: one issue row recorded once,
  rather than silence, even though the sub-calls may still each attempt their own GET. This is
  documented inline in the script's own header comment, not silently assumed.
- `PROJECT_ROOT` is resolved via `common_repo_root "$SCRIPT_DIR" 2` (from the script's own
  location, never from cwd) — the two production call sites
  (`orchestrate-cycle-postflight.sh`, `reconcile-task-status.sh`) do not guarantee cwd is the
  repo root when they invoke this script.

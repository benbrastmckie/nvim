## Key Decisions Made

- The existing-link guard is checked ONCE, before both the dry-run print and the confirmed POST
  (not only before the write), since it governs whether the bind invocation should proceed at
  all -- matching the plan's D1/D2 framing of bind mode as a single flow with two postures.
- **Non-obvious fix, worth knowing for Phase 3**: `sapience_post` (in `sapience-api-lib.sh`,
  untouched this phase) sets its caller-visible `sapience_api_post_http_status` as a plain,
  non-local assignment, but that assignment never reaches a caller that captures the function's
  stdout via `x="$(sapience_post ...)"` -- command substitution forks a subshell, and the
  assignment dies with it. The bind path instead redirects `sapience_post`'s stdout to a temp
  file (`sapience_post ... > "$tmp"`), which keeps the call in-process so the status assignment
  actually lands. The PRE-EXISTING create path still uses the `$(...)` form and therefore never
  sees a real status value (its `if [ "${sapience_api_post_http_status:-}" != "" ]` guard is
  always false there) -- this is latent, out of this phase's declared scope
  (`sapience-project-bind.sh`'s create path is unchanged behavior per the plan's Rollback
  section), and not something Phase 2 touched or needs to fix, but Phase 3's vendor-delegation
  fallthrough re-POSTs through this SAME bind-mode code path, so it inherits the fix for free.
  Recorded inline in the script (just above the `case` statement) and as an issue-log win entry.

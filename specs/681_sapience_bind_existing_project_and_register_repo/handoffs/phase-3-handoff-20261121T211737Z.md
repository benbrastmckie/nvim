## Key Decisions Made

- Followed the plan's D1 exactly: delegation applies only to `--project <value> --confirm`
  (never pick, never dry-run), and this script remains the sole writer by reading the vendor's
  file back and re-rendering it — byte-identity is enforced structurally, not hoped for.
- Classification is exit-code-and-file-presence only; `delegate_link()` redirects the vendor's
  stdout/stderr to `/dev/null` unconditionally, so no branch anywhere can be tempted to parse
  vendor prose later. Confirmed by grep at verification time.
- Test case 22's byte-identity proof uses two independently-built scratch repos sharing the same
  leaf directory name (`build_scratch_named`), so both resolve to the same `repo_slug`, and
  compares the two actual written files directly via `cmp` rather than against a third,
  hand-built expected-JSON file (stronger than cases 7/18's pattern, deliberately, since this is
  the byte-identity requirement itself).

## What NOT to Try

- Do not redeploy (`deploy-headless.sh`) from this phase or treat the deployed `.claude/` mirror
  staleness as something to fix here — the plan's own Risk table defers the redeploy to the
  orchestration close, and three concurrent sibling tasks would serialize against a whole-tree
  claim.
- Do not invoke the `sapience` binary on `$PATH` to detect or delegate `link` support — it is a
  packaged wrapper with a fixed `case` table, no `link` branch, and cannot reach
  `sapience_cli.py`'s own argument parser at all (confirmed in the research report). Always go
  straight at `$SAPIENCE_CLI_PATH` via `python3`.
- Do not parse vendor stdout/stderr text to classify anything — D1 forbids it structurally and a
  test (case 14 lockstep plus the header's own MUST NOT) would not catch a reintroduction of
  this, only the grep-based verification step does.

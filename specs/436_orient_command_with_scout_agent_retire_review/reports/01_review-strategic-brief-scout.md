## Findings

### Codebase Patterns

**`/review`'s current shape** (`agent-system/extensions/core/commands/review.md`): a direct-execution slash command (`allowed-tools: Read, Write, Edit, Glob, Grep, Bash(git:*), TaskCreate, TaskUpdate, AskUserQuestion`) with no agent dispatch anywhere in its 8 numbered sections. It never calls `roadmap-integration.sh` (confirmed by full-file read; the only roadmap-adjacent content is a static "`specs/ROADMAP.md` is hand-curated prose and is not mechanically parsed" note in the review-report template, and the Task Order goal-statement write in Section 6.7.3). Adding a strategic-brief mode means adding a new numbered section (or an argument branch) that dispatches the scout via the `Agent` tool and renders its returned text directly to the user -- the first `Agent`-tool dispatch `/review` will perform.

**Minimal read-only agent template** -- `code-reviewer-agent.md` is the closest existing precedent: frontmatter is just `name`, `description`, `model: sonnet` (no `tools:` line at all, so it inherits the default read-leaning set), body has an Overview/Metadata/Allowed-Tools-prose/Context-References/Checklist/Output-format/Return-Format structure, and it ends with "Return brief summary (3-5 bullet points)" -- i.e. console-only, no file writes, no `.return-meta.json`. This is the agent lint-agent-contracts.sh already classifies as "console-only return, no file-based metadata exchange" (see Check F below) and as "invoked only via the forked-subagent pattern... never reached through a skill-orchestrate dispatch row" (Check J). The new scout agent is structurally identical in both respects and should mirror both exclusion-array entries exactly.

**Frontmatter field for the tool allowlist is `tools:`, not `allowed-tools:`.** Per `docs/reference/standards/agent-frontmatter-standard.md`'s Supported Fields table and `lint-agent-contracts.sh`'s `SUPPORTED_KEYS` array (`name, description, tools, disallowedTools, model, ...`), a dispatchable agent declares its allowlist as a comma-separated `tools:` string, e.g. `spawn-agent.md`'s `tools: Read, Write, Glob, Grep, Bash(jq:*)` or `roadmap-agent.md`'s `tools: Read, Write, Edit, Bash`. For the scout, the correct form is `tools: Read, Grep, Glob, Bash` (no `Write`, no `Edit` token present at all -- satisfies the ACCEPTANCE bullet literally). Check A (`lint-agent-contracts.sh`) will `log_fail` on a stray `allowed-tools:` key if that skill/command-style spelling is mistakenly used instead.

**Bash access is not read-only by itself.** `general-research-agent.md` explicitly documents (its own "Local Wait Discipline" section) that it "carries no `## Allowed Tools` restriction section (Bash is unrestricted)... a strictly wider exposure" and compensates with explicit body-level MUST/MUST NOT prose, not frontmatter. The scout's frontmatter (`tools: Read, Grep, Glob, Bash`, no `Write`/`Edit`) prevents the two named GUI-level write tools, but `Bash` can still write files via shell redirection (`echo ... > file`). To make "read-only by construction" actually true rather than merely frontmatter-literal, the agent body should carry an explicit MUST NOT bullet forbidding any file mutation via `Bash` (e.g. redirection, `sed -i`, `cp`), analogous to how other agents state MUST/MUST NOT prose around their own unrestricted-tool hazards.

**Three ACCEPTANCE-gating scripts and what each actually requires of a new agent file:**

1. `validate-index.sh` -- orphan/missing-file/duplicate checks over `index-entries.json`'s `entries` array, plus a hardcoded six-agent budget-printing loop (`general-research-agent`, `planner-agent`, `general-implementation-agent`, `meta-builder-agent`, `code-reviewer-agent`, `spawn-agent`) that is informational only, not a pass/fail gate for agents outside that list. **Adding the scout requires no change here** unless the plan also adds a new, badly-scoped `index-entries.json` entry (which would then need to avoid the orphan/duplicate checks).
2. `validate-context-budgets.sh` -- a hardcoded `CAPS` associative array of exactly 10 agent names (not including `roadmap-agent`, `reviser-agent`, or `spawn-agent`'s... wait, `spawn-agent` IS in CAPS) is the only budget-enforcement surface; a new agent name absent from `CAPS` is simply never checked. **No change required** for the scout to pass this script, since nothing in the dispatch asks for the scout to be added to `CAPS`.
3. `lint-agent-contracts.sh` -- scans **every** file under `agents/` whose first line is `---` and whose frontmatter has a `name:` key (`enumerate_dispatchable_agents()`), i.e. the scout is automatically in-scope the moment the file exists, for Checks A, B, F, J, K at minimum (independent of any curated list):
   - **Check A** (frontmatter key validity): the scout's `tools:` key must be spelled correctly; `allowed-tools:`/`mcp-servers:` are hard FAILs.
   - **Check B** (model field): `model:` is required; omitting it is a FAIL.
   - **Check F** (return-meta artifacts template presence): FAILs unless the scout's path is added to `EXCLUDED_ARTIFACTS_TEMPLATE_RELATIVE_PATHS` (currently `code-reviewer-agent.md`, `literature-agent.md`, `roadmap-agent.md` -- all three justified as "console-only return, no file-based metadata exchange"). The scout is console-only by design (no Write tool at all), so it must be added to this array with the same justification, or Check F will demand an impossible `.return-meta.json` artifacts-shape block.
   - **Check J** (handoff-writing section requirement): FAILs unless the scout's path is added to `CHECK_J_EXCLUDED_RELATIVE_PATHS` (currently `code-reviewer-agent.md`, `meta-builder-agent.md`, `spawn-agent.md`, plus three extension agents -- all justified as "invoked only via the forked-subagent pattern... never reached through a `skill-orchestrate` `dispatch[]`/`aux_dispatch[]` row"). The scout, dispatched directly from `/review`'s own command body via the `Agent` tool (never through `skill-orchestrate`), fits this classification exactly and must be added here too.
   - **Check K** (await-notification antipattern absence): applies to every dispatchable agent but is an absence check -- passes automatically provided the scout's body never instructs backgrounding a process and then waiting for a completion notification. No action needed beyond not writing that pattern.
   - **Checks C, G, H, L, M, N** are scoped to curated path lists keyed by filename-glob nets (`*implementation*agent.md`, `*research*agent.md`) or explicit path arrays that do not currently include, and are not forced to include, a filename that contains neither "research" nor "implementation" (e.g. `orientation-scout-agent.md` or `scout-agent.md`). Naming the new file to avoid those two substrings keeps it out of Check N's forced-membership nets.
   - **This Check F / Check J requirement sits outside the dispatch's own FILE SCOPE paragraph**, which names only `agents/{new-file}`, `commands/review.md`, `manifest.json`, `index-entries.json` as edit targets -- `scripts/lint/lint-agent-contracts.sh` is not listed, yet editing its two curated arrays is mechanically necessary for the ACCEPTANCE bullet "Core's own lint and validate scripts pass" to hold. Flagged as a FILE SCOPE / ACCEPTANCE tension for the plan to resolve (most likely resolution: treat `lint-agent-contracts.sh`'s two array edits as an implicit, necessary extension of the stated scope, since the alternative -- leaving Check F/J red -- directly contradicts a named ACCEPTANCE bullet).

**`manifest.json` vs `index-entries.json` as "registries":** `manifest.json`'s `provides.agents` array (currently 8 entries) is the actual install/registry manifest `deploy-headless.sh` and `validate-wiring.sh`'s hardcoded-name checks key off; appending the new filename there is required. `index-entries.json`'s 177 `entries` are exclusively *context docs* (none of the 177 paths matches `agents/*.md` or begins `agents/`); an agent's own file is never itself an index entry. Existing agents are only *referenced* there via other docs' `load_when.agents` arrays (e.g. `standards/analysis-framework.md`, `standards/code-patterns.md`, and `workflows/review-process.md` all declare `load_when.agents: ["code-reviewer-agent"]`, each also scoped to `commands: ["/review"]`). Deliverable 3's "Registry entries ... in index-entries.json" is therefore satisfied either by (a) adding the scout's name to an existing relevant doc's `load_when.agents` array if the plan decides the scout should pull in an on-demand context file, or (b) no `index-entries.json` change at all if the scout's body is fully self-contained (as the dispatch's compact five-section/HARD-REQUIREMENTS design suggests) -- there is no precedent requiring a bare new entry for the agent file itself.

## Risks & Mitigations

- **Risk**: `lint-agent-contracts.sh` Checks F and J fail after the agent file is added, because the new agent isn't yet listed in that script's two curated exclusion arrays, and that script is outside the dispatch's stated FILE SCOPE. **Mitigation**: treat the two array edits as a necessary, implicit extension of FILE SCOPE (confirmed above); add them in the same phase as the agent-file creation, not as an afterthought.
- **Risk**: hardcoding the Lean/`FormalSystem`-specific paths from the dispatch's PURPOSE section directly into the (shared, cross-repo) `core` agent body, producing a scout that is broken or misleading in every consumer repo that isn't the Lean/formal-math one. **Mitigation**: read those paths only as existence-conditional probes (`[[ -f ... ]]` / `grep` guarded), never as unconditional reads; fall back gracefully (note their absence, do not error) when absent, as this nvim repo's own tree demonstrates is the common case.
- **Risk**: `Bash` being present in `tools:` undermines the literal "no Write, no Edit" ACCEPTANCE bullet's intent (a file can still be mutated via shell redirection even without the Write/Edit tool names). **Mitigation**: explicit body-level MUST NOT prose forbidding any file mutation via Bash, as recommended above.
- **Risk**: the stale task `title` is read by a later phase as the operative requirement (building `/orient`, deleting `/review`), reopening the exact scope reversal the description revision was meant to settle. **Mitigation**: this report's Executive Summary and Decisions sections record the authoritative shape explicitly, for the plan/implementation phases to consume directly rather than re-deriving from `state.json`'s title field.

## Executive Summary

- Both prerequisite building blocks already exist and are fully designed/tested: `lean-comparator-run.sh` (task 153, the sandboxed Comparator wrapper with a 9-verdict vocabulary) and `lean-challenge-snapshot.sh` (task 154, produces the immutable `Challenge.lean` + `specs/{NNN}_{SLUG}/challenge/manifest.json`, resolving the "no Challenge exists today" constraint). This task is pure **wiring**: read the manifest, invoke the runner, surface the verdict — it authors no new Lean-checking logic.
- The manifest (`specs/{NNN}_{SLUG}/challenge/manifest.json`) already carries everything the gate needs except `solution_module` and `permitted_axioms`: `project_root`, `challenge_module`, `challenge_path`, `theorem_names`, `commit`, `content_sha256`. The gate step should read this file with `jq`, not re-derive any of these values.
- Recommended default `permitted_axioms` for the gate: `propext,Quot.sound,Classical.choice` — the exact whitelist already vendored in the task-153 test fixture (`simple_match/config.json`) and consistent with `proof-debt-policy.md`'s "no *new* axioms" policy (the three foundational classical axioms are ambient, not new).
- A real integration risk not named in the dispatch's WORK list: the Challenge commit and the Solution commit are necessarily different (Challenge is committed at `planned`-time, immutably; Solution is committed only after implementation finishes). `lean-comparator-run.sh --commit REF` checks out **one** commit for both modules via a single `git worktree add --detach`. This is only safe because ordinary git history keeps `Challenge.lean` present, byte-identical, at every later commit unless something touched it — the gate step should pass `--commit <the post-implementation HEAD>` (not the manifest's `commit`) and independently verify `Challenge.lean`'s content at that HEAD still hashes to the manifest's `content_sha256` before trusting the run, defending against a tampered or accidentally-touched Challenge file. This check is cheap (a `git show | sha256sum`) and is not something `lean-comparator-run.sh` does for you.
- A genuine scope gap between the dispatch's WORK list and its ACCEPTANCE criteria: **no `/orchestrate`-level flag plumbing is named**. `orchestrate.md`'s options table has no `--compare` row, and neither `orchestrate-cycle-plan.sh` (line ~1476, where `lit_flag`/`hard_mode`/`effort_flag` are translated into `orchestrate-build-dispatch.sh` CLI args) nor `orchestrate-build-dispatch.sh` itself (lines 84-103, same set of flags) has any COMPARE-shaped counterpart. The dispatch's WORK items (a)-(e) only touch `parse-command-args.sh`, the two lean skills, the two lean agents, and `return-metadata-file.md`. If `--compare` is meant to be reachable via `/orchestrate N --compare` (which the ACCEPTANCE bullets' language — "a lean4 dispatch WITH --compare" — strongly implies), the plan MUST also add `orchestrate.md`'s options-table row and thread a `compare_flag` through `orchestrate-cycle-plan.sh`'s per-task `build_args` array and `orchestrate-build-dispatch.sh`'s own flag parsing/dispatch-file emission, mirroring the existing `--lit`/`--hard` treatment exactly. This is flagged here as a planning decision, not resolved by this report — the dispatch's author may have intended `--compare` to only be reachable by whatever mechanism the skill/agent's own delegation-context template already supports (see below), but as written today neither skill reads any per-invocation flag from its own delegation context at all (unlike e.g. `skill-python-implementation`, which has a `Stage 4a` reading `clean_flag`/`lit_flag`) — so *some* upstream mechanism must set `compare_flag` before the skill's Stage 3/4 can forward it.

## Context & Scope

Task 155 threads an advisory-only `--compare` flag from the command line down through: flag parsing -> the two lean implementation skills' delegation context -> the two lean implementation agents' Final Verification Stage -> `.return-meta.json`'s new `comparator` block -> the skill's postflight summary. The Comparator judge itself (`lean-comparator-run.sh`) and the Challenge-production tool (`lean-challenge-snapshot.sh`) are out of scope — both already exist, are tested, and their design records are binding. The gate strength decision (advisory only, never blocking, never downgrading status) is also already made and explicitly not to be relitigated.

## Findings

### Codebase Patterns

**Flag-spine precedent (`core/scripts/parse-command-args.sh`)**: `LIT_FLAG` and `CLEAN_FLAG` are the exact model named in the dispatch. Both follow the same 4-part pattern in this one file:
1. Header comment block (`# LIT_FLAG — "true" or "false" (--lit mode hint ...)`) — line ~22 for `LIT_FLAG`.
2. Default assignment in the flag-init block (`LIT_FLAG="false"`) — line ~91.
3. A single `if [[ "$remaining" =~ --lit ]]; then LIT_FLAG="true"; fi` block — line ~134.
4. A `sed 's/--lit//g'` strip in the `FOCUS_PROMPT` construction, and inclusion in the final `export` line (line 184).
`COMPARE_FLAG` should be added as a fifth boolean-hint variable identical in shape to `LIT_FLAG`/`CLEAN_FLAG` (never modeled on `EFFORT_FLAG`, which is a single mutually-exclusive enum slot the dispatch explicitly says not to compete with).

**Skill delegation-context precedent**: `skill-lean-implementation/SKILL.md`'s Stage 3 ("Prepare Delegation Context") and `skill-lean-implementation-hard/SKILL.md`'s Stage 4 both emit a JSON block that is handed verbatim into the `Agent` tool call in the immediately following stage. Neither skill currently threads *any* per-invocation flag (no `lit_flag`, `clean_flag`, or `effort_flag` reads exist in either file today — grep confirms zero matches in `skill-lean-implementation/SKILL.md` and only a hardcoded literal `"effort_flag": "hard"` in the hard variant). Adding `"compare_flag": "{true|false}"` to both JSON blocks is a direct, minimal-diff addition matching the existing field style (see `dispatch_seq`'s "forward unchanged, never invent" language in the hard skill's Stage 4 for the right tone to model the new field's documentation on).

**Agent Final Verification Stage precedent**: both `lean-implementation-agent.md` (steps 1-5, ending at "Plan compliance spot-check") and `lean-implementation-hard-agent.md` (Stage 6, steps 1-5) enumerate a fixed, numbered checklist ending in a `Record: ...` line and a failure-handling paragraph ("On Verification Failure" / "On verification failure"). A new Comparator step is a natural "step 6" appended after plan compliance in both files, gated behind `compare_flag == true` as its very first line (so the flag's absence produces literally zero new behavior — no invocation, no metadata block, no cost — exactly the first ACCEPTANCE bullet). Both files' failure-handling paragraphs currently list conditions that set `status: "partial"`; the new step's failure/rejection paths MUST NOT be added to that list (advisory-only), which needs to be stated explicitly in the new step's own text to avoid an editor accidentally folding it into the existing enumeration.

**Skill postflight precedent for reading (never re-running) agent-recorded results**: `skill-lean-implementation/SKILL.md` Stage 6b ("Plan Compliance Check (Read from Metadata)") is the exact template for item (e): it reads `jq -r '.metadata.compliance_check // "skipped"'` from the already-written `.return-meta.json` and echoes a loud, differently-worded message per case, explicitly noting "SKILL reads the result — MUST NOT re-run grep per postflight-tool-restrictions.md." A new Stage 6c ("Comparator Verdict Surface") should read `jq -r '.comparator.verdict // "not_run"'` (plus `reason_detail`/`message`) and print a loud line for any non-`verified` verdict, but — unlike Stage 6b's `compliance_check == "failed"` branch — must never set `status="partial"`, matching the ADVISORY MEANS ADVISORY directive verbatim. The hard skill has no equivalent Stage 6b/6c today (its postflight section was not grepped for one); the plan should confirm whether the hard skill needs an analogous surfacing stage or whether the base skill's postflight is shared.

**Metadata schema precedent for a new optional top-level object**: `return-metadata-file.md`'s `### completion_data (optional)` section (present, documented) is the template to copy for a new `### comparator (optional)` section — "Type: object", "Include if: ...", a field table, and a "Notes" bullet list. Note as an aside (not in scope for this task, but worth recording): the existing `verification` block (`verification_passed`, `sorry_count`, `vacuous_count`, `axiom_count`, `build_passed`) that the dispatch explicitly says "are NOT touched by this task" is *itself* undocumented in `return-metadata-file.md` today — grep found zero occurrences of any of those five field names in that file. The dispatch's instruction to document `comparator` (unlike its undocumented `verification` sibling) is a deliberate, stated improvement, not an oversight to "fix" by also documenting `verification` — that would be scope creep beyond this task.

### Recommendations

1. **Flag spine**: add `COMPARE_FLAG` to `parse-command-args.sh` exactly like `LIT_FLAG` (header doc line, default `"false"`, `--compare` regex match, strip in `FOCUS_PROMPT`, add to the final `export` line). Do not give it an enum shape.
2. **Manifest-driven gate invocation**: the new agent-side Comparator step should locate `specs/{padded_num}_${project_name}/challenge/manifest.json`, and if absent, emit a loud, named `comparator_unavailable`-shaped finding ("no Challenge manifest found; run `lean-challenge-snapshot.sh` before `--compare`") rather than silently skipping — this is a distinct failure mode from "missing binary" but should probably share the same verdict category value for the metadata block's consumer simplicity, or be a clearly-named 10th case; the plan should decide which.
3. **Commit selection**: pass `--commit <HEAD-after-implementation-commit>` (not the manifest's own `commit`), and add an explicit `git show <that-commit>:<challenge_path> | sha256sum` cross-check against the manifest's `content_sha256` immediately before invoking the runner — a drift here should itself be reported (loudly, advisory) rather than silently trusting a possibly-stale worktree checkout.
4. **`solution_module` derivation**: unlike `challenge_module`, no existing tool computes this. The plan needs to decide how the agent names the Lean module containing the just-implemented theorems (a `--solution-module` CLI value that must resolve to real, already-committed `.lean` source at the checked-out commit per the design record's precondition). The simplest option consistent with existing conventions is a `Theories.<PathDerivedModuleName>` dotted-module name matching wherever `grep -rl` found the plan's goal identifiers during the existing Stage-5 compliance check — that file discovery already exists in the agent and could be reused rather than re-invented.
5. **`permitted_axioms` default**: `propext,Quot.sound,Classical.choice` unless the plan names additional axioms explicitly (there is no existing plan-format field for this — the dispatch does not ask for one, so hardcoding the three-axiom baseline as the gate's default is the minimal, in-scope choice).
6. **Theorem-name source**: read `theorem_names` directly from the manifest (already cross-validated against the plan's `**Goals**:` bullets at snapshot time) rather than re-parsing the plan.
7. **Metadata block shape** (for the `.return-meta.json` `comparator` object, item (d)): mirror the runner's own `--json` output — `verdict`, `reason_detail` (optional), `underlying_verdict` (optional), plus the theorem names checked, the axiom whitelist used, and a runtime/duration figure (the dispatch explicitly asks for all of these). Example:
   ```json
   "comparator": {
     "ran": true,
     "verdict": "verified",
     "theorem_names": ["comm", "assoc"],
     "permitted_axioms": ["propext", "Quot.sound", "Classical.choice"],
     "runtime_seconds": 612
   }
   ```
   `"ran": false` (with no other fields required) covers the `compare_flag != true` case, letting a consumer distinguish "not requested" from "requested but comparator_unavailable."
8. **Documentation**: add `### comparator (optional)` to `return-metadata-file.md`, modeled on `### completion_data (optional)`'s structure, explicitly stating the advisory contract ("MUST NOT set `verification_passed` false, MUST NOT downgrade status, MUST NOT block completion") inline so a future reader of the schema doc alone (without the design record) still gets the binding constraint.
9. **Promotion-criteria record**: per the dispatch's closing paragraph, the implementation summary (not this report) should enumerate concrete, evidence-based promotion criteria (e.g. "N consecutive `verified` runs with zero `comparator_unavailable` results across M distinct target projects") so the later hard-gate decision has real evidence rather than vibes.

## Decisions

- Confirmed and treated as binding (not relitigated): advisory-only gate strength; `--compare` composes with `--hard` rather than competing with it (boolean hint, not an effort-flag value); the four named source files for the flag spine/skill/agent/metadata changes are exactly as the dispatch states.
- Left open for the planner (not resolved here, since resolving them is plan-authoring, not research): (a) whether `/orchestrate`-level flag plumbing (`orchestrate.md`, `orchestrate-cycle-plan.sh`, `orchestrate-build-dispatch.sh`) is in-scope for this task despite not being named in the WORK list, given the ACCEPTANCE criteria's dispatch-level test language; (b) the exact `solution_module` derivation mechanism; (c) whether a missing-Challenge-manifest condition should reuse `comparator_unavailable` or be a distinct verdict value; (d) whether `skill-lean-implementation-hard/SKILL.md` needs its own Stage 6b/6c-equivalent postflight-surfacing addition (its current postflight structure was not confirmed to mirror the base skill's Stage 6b).

## Risks & Mitigations

- **Risk**: a Comparator invocation silently no-ops if the manifest is missing (e.g., a lean4 task implemented without ever running `lean-challenge-snapshot.sh` first). **Mitigation**: treat "no manifest" as its own loud, named finding distinct from an honest `comparator_unavailable` (missing binary), so an operator can tell "the tool couldn't run" from "nobody ran the prerequisite."
- **Risk**: commit-selection mismatch (see Findings) — passing the wrong commit ref to `--commit` either fails to find the Solution module (not yet committed) or checks out a stale/tampered Challenge. **Mitigation**: explicit content-hash cross-check against `manifest.content_sha256` before trusting any run, as detailed above.
- **Risk**: cost (C4) — a `--compare` dispatch on a Mathlib-dependent project runs two full sandboxed builds, two exports, and a kernel replay (minutes to tens of minutes). **Mitigation**: already addressed by design — opt-in only, scoped to named theorems, bounded by `--timeout`; no further action needed in this task beyond preserving that opt-in gating.
- **Risk**: binary unavailability. As of 2026-09-07, `landrun`/`comparator` were reported present on the operator's host via home-manager (per the design record's "Binary Provisioning Status" section) but `lean4export`/`nanoda_bin` remain absent, and a direct `comparator` invocation independently hit a `lake`/landrun permission error before reaching the lean4export step. **Mitigation**: none needed for this task — `comparator_unavailable` is exactly the designed-for outcome for a missing/broken toolchain, and the ACCEPTANCE criteria explicitly requires demonstrating this path rather than a full green run.

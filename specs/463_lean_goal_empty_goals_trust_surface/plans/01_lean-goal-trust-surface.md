## Overview

The lean extension tells its implementation agent to verify step completion with `lean_goal`,
and simultaneously asserts in its tool reference that `"no goals" = proof complete`. That
equivalence is false: an elaboration error inside a tactic term closes the goal with a synthetic
`sorryAx` placeholder, so `goals_after` comes back empty while the declaration does not
elaborate. This plan states the trust surface once, in `mcp-tools-guide.md`'s `#### lean_goal`
section, names `lean_verify` on the fully qualified name as the cheaper-than-full-build check
that does cover the case, points the flow document's step-verification line at that statement
without restating it, and deletes the one in-scope restatement of the false equivalence from the
extension README's capability table. A final phase redeploys the tree and discharges the gate
obligation.

**The one open evidentiary gap in the research report is now closed.** The report flagged the
synthetic-`sorryAx`-on-elaboration-error mechanism as standard Lean behavior that it had not
independently re-derived. Planning measured it directly, on Lean 4.33.0-rc1, with a four-line
standalone probe needing no project or Mathlib import:

```lean
theorem probe_unknown : True := by
  exact Bool.true_ne_false_nope

#print axioms probe_unknown
```

`lean probe.lean` emits `error(lean.unknownIdentifier): Unknown constant
'Bool.true_ne_false_nope'` and then `'probe_unknown' depends on axioms: [sorryAx]`. The goal is
closed — which is exactly what `lean_goal` would report as an empty `goals_after` — while the
axiom profile shows the declaration does not elaborate. Phase 1 therefore writes the mechanism as
a measured claim with its toolchain pin, matching the evidentiary convention
`metadata-trust-surfaces.md` already sets for its own statements, instead of hedging it as
asserted standard behavior.
